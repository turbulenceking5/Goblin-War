# Goblin War

A browser-based overworld RPG. No build step, no framework — every page is a single self-contained `.html` file with inline `<style>` and `<script>`, opened directly or served as static files. Live gameplay state lives in `localStorage` while playing, shared across pages by convention (same key names, no formal schema) — but the durable copy is a row in Supabase (hosted Postgres + auth), talked to directly over its JS client loaded from a CDN `<script>` tag (no server code of ours, just a public anon key and Row Level Security). **Every player page requires a logged-in account with an active character** (see [context/accounts.md](context/accounts.md) and [context/characters.md](context/characters.md)) — an account can own a roster of characters, picked at login, one save per character, autosaved as you play.

**Single-player only, per the project owner.** Every account's characters, world, kingdoms, and wars are entirely its own — Supabase's `characters` table exists for durable cross-device saves, not for any shared or synced state between different accounts. Nothing in the game (armies, factions, quests, the map) is meant to involve or be visible to other real players; don't scope a feature (leaderboards, shared worlds, trading between accounts, PvP) that would require otherwise.

Fictional setting only — "Goblin War" and its world data have no connection to any real organization, event, or person.

**Live at [turbulenceking5.github.io/Goblin-War](https://turbulenceking5.github.io/Goblin-War/)** — GitHub Pages serving this repo's static files directly, no build/deploy step beyond pushing to the branch it's configured against.

## Conventions worth knowing before editing

- **No modules, no bundler.** Each HTML file's `<script>` is copy-pasted, self-contained JS — shared logic (e.g. the calendar formatter, the `localStorage` key names) is duplicated across files rather than imported. When you change a constant or a formula in one page, check the others for the same duplicated logic. The one deliberate exception is the login gate (`assets/auth-gate-sync.js` + `assets/auth-client.js`, see [context/accounts.md](context/accounts.md)) — genuinely shared, not copy-pasted, because it's security-relevant control flow rather than game logic: one page's copy silently drifting from another's would be a login bypass, not just a display bug.
- **Shipping a change? Add a `changelog.json` entry, and bump `version.json`.** `changelog.json` (an array of `{id, date, changes}`) is the single source both index.html (drives the "What's New" popup shown on map load once the viewing account's `goblinwar_lastSeenChangelog_<user id>` falls behind the newest id — see [context/accounts.md](context/accounts.md)) and changelog.html (renders the full history, and bumps that same key so visiting it doesn't also trigger the popup) fetch it from — no more hand-duplicated array to keep in sync. Add one new `{id, date, changes}` entry — id one higher than the last — whenever a player-visible change ships. Also bump `version.json`'s `changelogId` to match — that's what index.html's "Update available" banner polls to know a newer build exists on the server; forgetting it means the banner never fires for that release.
- **Dark theme, kept consistent across pages.** Every page (except the unused game-map.html) uses the same dark-parchment palette: page/card backgrounds are near-black warm browns (`#1c150c` page bg, `#2b2115`→`#1c150c` gradients for raised cards/sheets/modals), body text is `var(--parchment)` (`#e9dcb8`), muted/label text is `#a9926a`, and card borders are a soft translucent gold (`rgba(209,164,69,.35)`, `.4` on inputs/buttons) rather than the old solid `var(--parchment-shadow)`. `var(--gold)`/`var(--gold-lt)` stay the same in both — they already read well on dark. Match these tokens when adding new UI rather than reintroducing a light card.
- **No native `confirm()`/`alert()` dialogs for a destructive action — use the themed confirm modal.** Every page with a destructive click (Dismiss/Part Ways on party.html, Abandon on quests.html, Delete This Character on settings.html, Delete on characters.html) has its own small, duplicated `#confirm-modal`/`showConfirm(message, onConfirm)` (same dark-card styling as every other modal in this file's "Dark theme" bullet above) rather than the browser's own native `confirm()`, which breaks the pixel-art theme — per the project owner. `showConfirm` is the async-callback equivalent of the native `if(!confirm(message)) return; ...` pattern it replaces: wrap whatever ran after that guard in the callback instead (an `async` callback where the original code needed to `await`, same as characters.html's/settings.html's own Delete handlers). A new destructive action on one of these pages should follow the same pattern rather than reaching for `confirm()` again; a brand-new page needing one should copy the existing markup/CSS/JS block verbatim, per the no-modules convention below.
- **`localStorage` holds the live game; Supabase holds the durable save.** While playing, every page reads/writes the same `goblinwar_`-prefixed `localStorage` keys (e.g. `goblinwar_health`) as before — see [context/player-state.md](context/player-state.md) for the full list. But that's no longer the only copy: the active character's row in Supabase's `characters` table is autosaved from it periodically (see [context/characters.md](context/characters.md)), and is what actually survives across devices, browsers, or a cleared cache. Don't add a new persisted key to `localStorage` alone and assume it's safe — if it should survive a save, it needs to be added to the snapshot shape characters.md describes too.
- **Every internal navigation cache-busts with `?_=' + Date.now()`.** The game is deployed as static files behind a CDN with real HTTP caching (GitHub Pages: `Cache-Control: max-age=600`), and installed home-screen PWAs can hold onto stale pages even longer than that. Without a cache-buster, tapping a nav button or "Back to Map" shortly after a new version ships can silently reopen the *previous* version of that page — this actually happened (Settings kept showing the old inline Change Log after an update). So every same-app link — nav icons, "Back to X" buttons, post-action redirects (`location.href`/`location.replace`) — appends a timestamp query param, forcing a fresh fetch instead of a cache hit. `index.html`'s own "Update available" banner reload already did this; it's now consistent everywhere. A new nav link needs the same treatment. [sw.js](sw.js)'s own registration (every page, near `</body>`) follows the same convention for the same reason — a bare `'sw.js'` URL could let the CDN keep handing back a stale copy of the worker script itself.
- **Map coordinates are dual-scale.** World data (the procedurally generated world, SVG overlay) uses a 2560×1277 "logical" space; the raster canvas `renderWorldRaster()` paints is 10240×5108 (4× that). `STAGE_W/LOGICAL_W` converts between them — see [context/travel-and-map.md](context/travel-and-map.md).
- **Tone/flavor text is Chatty English fantasy** (rumours, ambush messages, location descriptions) — match that voice when adding more.
- **Full-screen overlays are z-index layered, and it's easy to get wrong.** index.html stacks `#location-view` (60), `#combat-view` (70), and `#toast` (80, deliberately above both) on top of the normal map UI. `showToast()` can fire from inside either overlay (Work, Inn, Marketplace, combat results), so the toast must outrank every overlay it can be called from, not just the base map chrome — it was briefly rendering invisibly behind `#location-view` for exactly this reason. If you add a new full-screen overlay, either give it a z-index below 80 or bump the toast again.
- **`env(safe-area-inset-*)` matters on installed iOS home-screen apps.** `viewport-fit=cover` (every page's viewport meta) lets content draw under the notch/status bar and home indicator; every sticky/fixed element pinned to a true screen edge — headers, `#toast`, `#travel-controls`, `#recenter-btn`, `#camp-here-btn`, `#info-card`, `#loc-actions`, `#combat-header` — adds the relevant `env(safe-area-inset-top/bottom)` into its own padding/position so it doesn't get clipped there. A new fixed-position element needs the same treatment; it's easy to miss on a new full-screen overlay specifically, since those don't inherit the normal `<header>`'s padding — `#loc-actions`'s "Back to Map" button and `#combat-header`'s title were both found clipped under the notch after being added without it.
