# Accounts (login gate)

Every player page requires a logged-in Supabase account *and* an active character — there's no way to reach the game, or even see it flash on screen, without both. The character half (choosing/creating who you're playing as, one save per character) is its own system — see [characters.md](characters.md) — but the two gate scripts described here enforce both checks together, so this file covers the mechanism and characters.md covers what it's gating access to.

## The gate itself

Two shared scripts, loaded on every gated page — index.html, character.html, skills.html, inventory.html, party.html, settings.html, changelog.html, characters.html (not game-map.html, which is unlinked dead code per the root [CLAUDE.md](../CLAUDE.md) and isn't gated). `login.html` and `characters.html` each opt out of part of the gate below — see their own notes.

1. **`assets/auth-gate-sync.js`** — loaded synchronously as the very first thing in `<head>`, before any CSS or body content. No network call: it checks whether *any* Supabase session token exists in this browser's `localStorage` (Supabase's own key, `sb-<project-ref>-auth-token`, derived from `SUPABASE_URL`) — if not, redirects to `login.html?redirect=<page>`. If a token's present, it then checks `localStorage.getItem('goblinwar_activeCharacterId')` — if that's missing, redirects to `characters.html?redirect=<page>` instead. Either redirect happens before a single frame of gameplay paints. It can't tell if a present token has actually *expired*, or if a present character id still refers to a character that actually still exists.
2. **`assets/auth-client.js`** — loaded near the bottom of the page, right after the Supabase JS CDN script, alongside each page's own inline script. It creates the one shared client (`const sb`), and does the real checks the sync pass can't: `sb.auth.getSession()` actually validates the token, and (for every page except characters.html) a follow-up query confirms the active character id still exists and still belongs to this account — covering both "the token expired" and "the character was deleted from another device" without the sync check's blind spots. It also listens for `SIGNED_OUT` (fired if the player logs out in another tab, or triggers `sb.auth.signOut()` on this one) and clears the active-character id + redirects then too, so a stale tab can't keep playing after logout elsewhere. Exposes a promise, `authGateReady`, that resolves to the session once every check passes (or `null`, in which case a redirect is already underway) — any page logic that needs to know who's logged in (e.g. the per-account changelog key, below) waits on this rather than calling `getSession()` again itself.

Both are genuinely shared files, not duplicated per page — the project's usual [no-modules convention](../CLAUDE.md) is to copy-paste logic per page, but login is security-relevant control flow: one page's copy silently drifting from another's would be a login bypass, not just a display bug worth living with.

`login.html` skips the gate scripts entirely (checking for an *existing* session itself, and redirecting onward if it finds one — see below). `characters.html` loads both gate scripts like any other page — it still needs a valid login — but both scripts special-case it, skipping only the "active character" half of the check, since it's obviously where one gets picked.

`login.html` is four toggled views in one card rather than separate pages: **Log In** (default), **Sign Up** (email + password, reached via a "New here?" link so the two flows aren't presented as two buttons on the same form — that was confusing), **Check your email** (shown after `signUp()` returns no session, meaning Supabase requires email confirmation first — the confirmation link's own landing is handled by the next view, not this page reloading), and **You're authenticated!** (shown whenever the page loads and already finds a valid session — either a stale link to login.html, or, more commonly, the confirmation email's link just handed `supabase-js` a session via the URL hash). On a normal login/signup, the player is sent straight to `characters.html?redirect=<target>` — **not** straight to the target page — carrying along wherever `?redirect=` originally pointed (or `index.html` by default) for characters.html to forward on once a character's actually been picked. See [characters.md](characters.md) for why login always routes through character selection.

**The "You're authenticated!" view is a dead end the player has to act on, not an auto-continue.** Per the project owner, clicking a confirmation-email link should read as "you're confirmed," full stop — not silently continue on into character select/the game after a pause, which is what it used to do (a 900ms `setTimeout` before redirecting). It now just shows the confirmed email address and a "Continue to the Game" button that calls the same `targetPage()` navigation on click — no timer, no automatic redirect. This applies to both cases that land here (a genuinely fresh email confirmation, or simply revisiting `login.html` directly while already logged in) since `sb.auth.getSession()` can't reliably distinguish the two from a plain hash check once `supabase-js` has already consumed and stripped the URL hash — same button either way.

**It nudges toward the installed Home Screen app, but can't actually launch it — that's a hard platform limit, not a gap here.** The project owner asked for the confirmation button to open the installed app rather than continue in the browser, but no web API on iOS or Android lets a page running in an ordinary browser tab launch an already-installed PWA — browsers deliberately don't expose that, the same way a website can't launch other unrelated apps on your device. This matters here specifically because a confirmation email's link *always* opens in the plain browser, never the installed app, even when one exists. `isStandaloneApp()` (`window.matchMedia('(display-mode: standalone)').matches || navigator.standalone === true`) is the closest available signal — true only when this page is itself already running as the installed app. When it's false, a hint (`#authed-app-hint`) tells the player to open Goblin War from their Home Screen instead — the button itself still works as a same-browser fallback (unchanged `targetPage()` navigation) for anyone who hasn't installed it, since there's no way to tell "not installed" apart from "installed but not currently open" from outside the app.

**The confirmation email's link is a Supabase project setting, not something the client code alone controls.** `signUp()` passes `emailRedirectTo: location.origin + location.pathname` (i.e. wherever login.html is actually hosted), but Supabase only honors that if the exact URL is allow-listed in the dashboard under Authentication → URL Configuration → Redirect URLs — otherwise it silently falls back to the project's Site URL instead. A Site URL that doesn't include the game's real path (e.g. a bare `https://<user>.github.io/` instead of `https://<user>.github.io/Goblin-War/`) is exactly what produced a 404 on the confirmation link before this was set up — the token in that link was valid, only the page it pointed at didn't exist. This is a one-time dashboard configuration step; nothing in the repo can do it.

## What the gate does *not* do

The gate itself never silently pulls or pushes character data — it only ever redirects to characters.html when no character is active, and it's characters.html's explicit Play/Create actions (not the gate) that actually write character data onto the live `goblinwar_*` keys. This sidesteps an earlier design problem: an early version of this project had login optionally auto-load a single cloud save, which risked silently overwriting more recent local progress with a stale cloud copy. Making character selection an explicit, always-required step (see [characters.md](characters.md)) rather than something login does automatically means there's never a question of which side "wins" — the player is always the one choosing what loads.

## Per-account "seen the changelog" state

`goblinwar_lastSeenChangelog` (index.html's "What's New" popup, and changelog.html marking itself as read) is namespaced per logged-in account — `goblinwar_lastSeenChangelog_<user id>` — rather than one flat key. `CHANGELOG_SEEN_KEY` starts `null` in both pages and is only set once `authGateReady` resolves with a session; anything that reads/writes it (`checkForWhatsNew()`, the dismiss handler, `renderChangelog()`) guards against it still being `null`. This means the popup's "seen" state is tied to *who's logged in*, not to the browser — one player dismissing it never marks it seen for a different account on the same device, and the same player logging into a second device still sees whatever they personally haven't seen yet (instead of every new device replaying the whole history, which the old flat per-browser key would have caused now that login exists).

**Migration from the old flat key.** The very first time a given account's namespaced key is read, `localStorage.getItem(CHANGELOG_SEEN_KEY)` is naturally `null` — indistinguishable, on its own, from "this is this player's first-ever session, nothing to compare against yet" (the case that's meant to go silent and just mark latest-as-seen). Without help, *every* account's first login would hit that silent case, even a player who'd been actively testing the game before login existed and has real "seen" progress sitting under the old flat `goblinwar_lastSeenChangelog` key in that browser — this was an actual bug hit during development (a click on the "Update available" banner reloaded the page, and the popup never appeared even though new entries existed). `checkForWhatsNew()` now falls back to reading the legacy flat key (`LEGACY_CHANGELOG_SEEN_KEY`) whenever the namespaced key is still `null`, and treats that as the starting point if present. A browser with neither key — a truly first-ever player — still falls through to the original silent "mark latest, show nothing" behavior.
