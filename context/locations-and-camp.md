# Locations & Camp (index.html)

Two full-screen overlays (`#location-view`, shared markup, z-index 60) that show up in different contexts: arriving at (or re-entering) a settlement, versus stopping mid-journey. Both use the same shell — `#loc-banner`, a full-width `position:fixed` banner pinned to the very top of the screen (`z-index:62`, above the scrolling list) showing the location's `TIER_ART`/`CAMP_ART` SVG, with `#loc-actions` (the full-width, full-height scrollable list of action buttons) padded at the top to clear it — just populated differently per context. `#loc-banner-portrait`, an absolutely-positioned child of the banner, overlays a talking character's portrait on top of that same art when one is showing (currently only `showNotableFigurePanel` — see below) — cleared again by `showLocationView`/`showCampView`'s own reset whenever the player leaves that panel or the settlement. This used to be a small `position:fixed` box pinned to the bottom-right corner (112×130px) instead of a top banner; moved per the project owner's request so a settlement's art reads as the scene the player just walked into, and so a talking character's portrait has a backdrop to sit on.

## Settlement view — `showLocationView(burgId)`

Reached by tapping "Enter Settlement" / "Travel Here" on a burg you're already at, or automatically on arrival after travel (post-ambush-roll, see [combat.md](combat.md)).

- The banner picks an SVG from `TIER_ART` (`village`/`town`/`city`/`capital` — four hand-drawn building illustrations, no per-settlement art).
- `checkQuestTurnIns(burgId)` (see [quests.md](quests.md)) runs first, before anything renders — so arriving at (or re-entering) a settlement that completes a Deliver a Message quest pays out immediately.
- The action list is a small array of `{icon, title, desc, action}` objects rendered identically. Every settlement gets the same base five:
  - **The Tavern** (`action:'tavern'`) → `showTavernPanel(burgId)` — see "The Tavern" below.
  - **Marketplace** (`action:'market'`) → `showMarketPanel(burgId)`.
  - **Work** (`action:'work'`) → `doWork()`, straight from the action list with no sub-panel — see "Work" below.
  - **Talk to Townsfolk** (`action:'talk'`) → `showFlavorPanel(burgId, 'Talk to Townsfolk', getTownsfolkLines(burgId))` — see below and [roadmap.md](roadmap.md).
  - **Quest Board** (`action:'questboard'`) → `showQuestBoardPanel(burgId)` — see [quests.md](quests.md).

  City- and Capital-tier settlements get more on top, appended conditionally by `b.tier` before the array is rendered — deliberately so a big settlement has more to actually do, not just a fancier building icon:
  - **Temple** (`action:'temple'`, City + Capital) and **Guard House** (`action:'guardhouse'`, City + Capital) → `showFlavorPanel(burgId, title, LINES)`.
  - **Blacksmith** (`action:'blacksmith'`, City + Capital) → `showBlacksmithPanel(burgId)` — see "The Blacksmith" below.
  - **Notable Figure** (`action:'notable_figure'`) → `showNotableFigurePanel(burgId)` — the important-quest counterpart to the Quest Board. Unlike Temple/Guard House/Palace, tier isn't the only gate: this only appears at the handful of specific settlements pinned as a named figure's home, and only while that home hasn't been captured — see [quests.md](quests.md).
  - **The Palace** (`action:'palace'`, Capital only) → same `showFlavorPanel` pattern, one tier further.

  Two more actions can appear at *any* settlement, any tier, independent of the tier-gated list above — pushed on conditionally right before render, same as the tier checks:
  - **Defend the Walls** (`action:'defend_walls'`) → `triggerSiegeDefenseFight`, whenever `goblinwar_sieges[burgId]` has an active siege — see [factions-and-territory.md](factions-and-territory.md)'s "Player involvement".
  - **Refugee Camp** (`action:'refugee_camp'`) → `showFlavorPanel(burgId, 'Refugee Camp', REFUGEE_LINES, buildRefugeeAidHTML(burgId))`, whenever `hasRecentRefugeeArrival(burgId)` is true — same file, same section.

  Temple/Guard House/Palace/Talk to Townsfolk/Refugee Camp all route through one shared `showFlavorPanel(burgId, title, lines, extraHTML)` rather than near-copies of `showInnPanel` — it picks a random line from whichever pool is passed in and renders one Back button + one quote box, plus whatever `extraHTML` is passed. Temple stays pure flavor with no mechanical effect, same as Talk to Townsfolk (`TEMPLE_LINES`/`GUARDHOUSE_LINES`/`PALACE_LINES`/`REFUGEE_LINES`, 5 lines each, same flavor-only pattern as `RUMOURS`); Guard House, The Palace, and Refugee Camp all pass real `extraHTML`: Guard House's `buildGuardHouseStats(burgId)` renders that settlement's real population, its current controller's own mustered strength, and (new) a siege-progress row when one is underway (population-derived — see [factions-and-territory.md](factions-and-territory.md)); The Palace can now render up to two cards together — `buildPalacePetitionHTML(burgId)` ("Petition for Troops," Alliance reinforcement, whenever this Capital's own kingdom is at peace and an ally needs help) and `buildNegotiatePeaceHTML(burgId)` ("Negotiate Peace," whenever this Capital's own kingdom has an active war relation) — both buttons wired by one shared `wirePalaceButtons(burgId)` since either or both cards can be showing; and Refugee Camp's `buildRefugeeAidHTML(burgId)` renders an "Aid the Refugees" donation card. See [factions-and-territory.md](factions-and-territory.md)'s "Player involvement" section for the full mechanics behind all three of the new pieces.

  **Talk to Townsfolk** is the one pool `showFlavorPanel` receives that isn't a single static array: `getTownsfolkLines(burgId)` assembles it fresh per visit from `TOWNSFOLK_LINES_PEACE` or `_WAR` (via `isAtWarAt(burgId)`, the same check Marketplace pricing uses below), plus `TOWNSFOLK_LINES_VILLAGE` or `_CITY` (by `b.tier`), plus `TOWNSFOLK_LINES_CAPTURED` on top whenever `getController(burgId) !== b.race` — reacting to *this* settlement's own situation rather than being universal world gossip like `RUMOURS`. Deliberately flavor-only, same as Temple — no mechanical effect, no quest hooks, no real NPCs (those stay separate, unscoped ideas — see [roadmap.md](roadmap.md)).
- `loc-back` (the `&larr; Back to Map` button) just hides the overlay — no state changes.

### The Tavern — `showTavernPanel(burgId)`

**One location, not two.** Used to be a separate Inn (rest + rumours, every settlement) and Pub (Meal & Drink, City/Capital always, Town sometimes via a seeded coin flip, Village never) — the project owner later called that split confusing (why would a settlement's rest stop and its food-and-drink stop be two different buildings?) and asked for them merged. Every settlement's Tavern now offers all three services below unconditionally; `hasPub(burgId)`/`PUB_TOWN_CHANCE`'s tiered gating and the separate `action:'pub'` button are gone, not just renamed.

Replaces the action list in-place (same `#loc-action-list` container) with a `render()` closure — called once on open and again after either action below, rather than patching individual elements — showing, in order:
- **Rest for the Night**: `advanceDays(1)`, then `restFully()` — full heal (`setHealth(playerMaxHealth)`) plus a stamina refill that overflows past `playerMaxStamina` by `BEDROLL_STAMINA_BONUS` (15) whenever a Bedroll is carried (written directly to `playerStamina`, bypassing `setStamina`'s own clamp — see [player-state.md](player-state.md)'s Stamina section for why that overcap is deliberate), then a toast (with an extra "Your bedroll leaves you extra rested" line when the bonus applied). No ambush roll here — Taverns are the safe option (contrast with camping, below). Resting does **not** touch Hunger or Thirst — see [player-state.md](player-state.md)'s Hunger & Thirst section on why that's deliberate. Health and stamina are the only two things resting ever touches.
- **Meal & Drink** (`buildTavernMealHTML()`, the old Pub's card): costs `TAVERN_MEAL_GOLD_COST` (12g, toast + no-op if short), then `addHunger(-TAVERN_MEAL_HUNGER_RELIEF)` and `addThirst(-TAVERN_MEAL_THIRST_RELIEF)` (both 50) — a full meal and a drink in one instant purchase, pricier per point of relief than buying Food/Waterskin outright but with zero weight or inventory management, the convenience option for a player who'd rather not carry consumables at all. See [player-state.md](player-state.md)'s Hunger & Thirst section for the meters it satisfies.
- **Tavern Talk**: a random line from `RUMOURS` (17 flavor-text strings — the old, separate `PUB_LINES` pool got folded straight into `RUMOURS` when the two locations merged, rather than kept as a second pool for one screen — no mechanical effect, pure world-building color), rerolled on every `render()` so it's fresh again after either action above.
- **Back** returns to `showLocationView(burgId)`, i.e. one level up, not the map.

### Work — `doWork(burgId)`

No sub-panel, just an immediate result straight from the settlement action list — but gated by a per-settlement, once-per-day cooldown. `hasWorkedToday(burgId)` checks `goblinwar_workCooldowns` (a `{burgId: gameDay}` JSON map, read/written via `getWorkCooldowns()`/`recordWorked()`) against the current `gameDay`; `showLocationView` calls it while building the action list, so a settlement already worked today renders its Work button `disabled` with the description swapped to "Already worked here today — come back tomorrow" (native `disabled` buttons don't fire `click` at all, so `doWork`'s own cooldown check at the top is a fallback, not the primary gate — same belt-and-suspenders pattern as combat's Attack button). Because the cooldown key is `gameDay`, not a real-world timer, it clears whenever the calendar actually advances — resting at an Inn/camp (always +1 day) or a long enough journey (see [travel-and-map.md](travel-and-map.md)) — not by waiting in real time.

When it's available: picks a random gold amount in `[3,15]` (`randRange`, same helper combat uses), adds it via `setGold(playerGold + earned)`, calls `recordWorked(burgId)`, shows a toast built from a random line in `WORK_LINES` (5 flavor strings) plus the amount earned, and re-renders the panel with `showLocationView(burgId)` so the now-disabled Work button and its cooldown message show up immediately rather than only after leaving and re-entering. No time cost — `gameDay` isn't touched by working itself — and no stamina cost either (stamina is combat-only, see [player-state.md](player-state.md)/[combat.md](combat.md)).

### The Marketplace — `showMarketPanel(burgId)`

The only shop in the game, and the only source of Food besides whatever you start with. Sells everything in the `MARKET_ITEMS` array (index.html, near `DEFAULT_INVENTORY`) — Food, Sword, Shield, Leather Cap, Leather Armour, Leather Boots, Lucky Charm, Healing Potion, Books, Firewood, Waterskin, Bedroll, and Horse — each with its own `{name, price, weight, desc}`, plus `slot`/`dmg`/`def` on the equippable ones (see [player-state.md](player-state.md) for the full equip table). Horse is the newest non-equippable entry — carried (not consumed, no slot), it speeds up overland road travel; see [travel-and-map.md](travel-and-map.md)'s "Horse and ferry fares" section for the mechanic:
- Shows current gold and carried weight (`getCarriedWeight()`/`CARRY_CAPACITY`) up top, then one row per `MARKET_ITEMS` entry (price/weight-per-unit, current carried amount from `getItem(name)`), each with a quantity **slider** (`<input type="range">`, `data-slider`) instead of fixed Buy 1/Buy 5 buttons, a live readout (`#qty-readout-N`, updated on the slider's `input` event without a full re-render), and one **Buy** button that reads the slider's current value.
- Each slider's `max` isn't a flat number — `render()` computes `Math.min(MAX_SLIDER_QTY (30), affordableQty, capacityQty)` per item, so you can never drag past what you could actually afford or carry at render time (though gold/weight can still change between renders from other purchases, which is what the real gate in `buyItem` is for — the slider max is a UX convenience, not the source of truth).
- Buy buttons carry a `data-buy` index into `MARKET_ITEMS` (not a fixed qty) rather than one hardcoded handler per item, so adding a new item to `MARKET_ITEMS` is enough — no new wiring needed in `render()`.
- `buyItem(mi, qty)` (generalized from the old Food-only `buyFood`) checks gold first (toast + no-op if short), then calls `addItem(mi.name, qty, mi.weight, mi.price)` (toast + no-op if it would exceed `CARRY_CAPACITY` — see [player-state.md](player-state.md)), and only deducts gold (`setGold`) if the item was actually added. Order matters here: a failed weight check must never have already spent the player's gold.
- Re-renders itself in place after every purchase or sale (`render()` is a closure over `burgId`/`list`, called initially and after `buyItem`/`sellItem` succeed) so the gold/weight/carried numbers — and every slider's recomputed `max` — stay current without leaving the panel. Sliders reset to `1` on every re-render; there's no "remember what I had the slider set to" behavior.
- Buying doesn't equip anything — a bought Sword just joins the bag like Waterskin/Bedroll always have. Equipping happens on inventory.html, not here — see [player-state.md](player-state.md) and [secondary-pages.md](secondary-pages.md).
- **Prices aren't flat anymore.** Every Buy slider/button and the new **Sell** button (below) price off `getBuyPrice(mi, burgId)`/`getSellPrice(mi, burgId)`, not `mi.price` directly — a kingdom at war charges more to buy and pays a premium to sell its war-relevant goods back. A banner at the top of the panel (`"{kingdom} — At war — prices up"` / `"At peace"`) makes the current state visible before you commit to anything. Full pricing mechanics (the multipliers, what counts as "war-relevant", how the kingdom's war state is looked up) live in [factions-and-territory.md](factions-and-territory.md), since they're shared with the faction-AI system that actually moves kingdoms in and out of war.
- **Settlement specialties — a small "shopping around matters" discount.** `getSettlementDiscount(mi, burgId)` (index.html, folded into `getBuyPrice`) checks `graph.burgs[burgId]`'s own `port`/`tier` fields (already in `travel-graph.json` — see [data-files.md](data-files.md), no new data pipeline needed): a port settlement (`b.port`) sells Waterskin at `PORT_WATERSKIN_DISCOUNT` (0.8×), and a Village (`b.tier==='village'`) sells Food at `VILLAGE_FOOD_DISCOUNT` (0.85×). Both discounts show as a small note under the war-state banner when applicable. This is a scoped-down version of [roadmap.md](roadmap.md)'s "Settlement specialties" idea — the original ask (a mountain Town discounting armor) needs elevation/biome data the live game doesn't pull through yet, so this picks two discounts the data actually supports instead.
- **Equip slot shown before buying.** Every equippable row (`mi.slot` truthy) now shows an "Equips: {slot label}" tag next to its price/weight line (`EQUIP_SLOT_LABELS`, index.html) — previously the only way to learn what an item equipped to was to buy it and check inventory.html. Purely a display addition; buying still never auto-equips.
- **Selling** (`sellItem(mi)`) is new: any carried item that's also a `MARKET_ITEMS` entry gets a "Sell 1 for Ng" row once you're carrying at least one (checked fresh every render, so it appears/disappears as your bag changes). Always sells exactly 1 at a time — no bulk-sell slider like buying has. Waterskin and Bedroll aren't in `MARKET_ITEMS`, so, like buying, they can't be sold either.
- Blacksmith-exclusive gear (`mi.shop === 'blacksmith'`, see below) is filtered out of this panel's rows entirely — the Marketplace never sells it.

### The Blacksmith — `showBlacksmithPanel(burgId)`

A second real shop, City + Capital only (same tier gate as Temple/Guard House) — exactly the extension this file's own "Adding a new location action" section (below) already named `showMarketPanel` as the template for ("an Armorer"). Deliberately a near-duplicate of `showMarketPanel`'s `render()`/`buyItem()`/`sellItem()` rather than a shared function, per the no-modules convention — the two shops' item lists are different enough (a filter over `MARKET_ITEMS` either way) that factoring them together would just mean passing a predicate through anyway.

- Sells only the `shop:'blacksmith'`-tagged `MARKET_ITEMS` entries: Masterwork Sword, Reinforced Shield, Steel Helm, Plate Armour, Steel Greaves, and Warrior's Talisman — a masterwork counterpart to each of the 6 core Equipment slots (see [player-state.md](player-state.md)), roughly double the `dmg`/`def` bonus at roughly triple the Marketplace price. This is the first real answer to the Equipment section's long-standing "no rarity/tier variation — a Sword is always +4, forever" gap: a second fixed tier via a second item name, not a per-instance upgrade system (inventory still stacks by name/qty, so there was no clean way to let one specific Sword be "upgraded" without a bigger rework).
- Otherwise byte-for-byte the same shopping experience as the Marketplace: quantity sliders capped by affordability/carry weight, `getBuyPrice`/`getSellPrice` war-pricing (a masterwork weapon is just as war-relevant as a basic one — `isWarRelevant(mi)` only checks `!!mi.slot`), the same "Equips: {slot}" tag on every row, a Sell row once you're carrying at least one, and buying never auto-equips — that's still only inventory.html's job.

### Adding a second shop of your own

`showMarketPanel` is still the template to copy (see "Adding a new location action" below) — `showBlacksmithPanel` is a worked second example of doing exactly that: same `render()`/`buyItem()`/`sellItem()` shape, a different filter predicate over `MARKET_ITEMS` (`mi.shop === 'yourshop'` instead of the default unflagged/`market`), and its own tier gate pushed onto `showLocationView`'s `actions` array.

## Camp view — `showCampView(destId, destName, partialHours)`

Two ways in, distinguished by `const standalone = !destId`:
- **Mid-journey**: `stopTravel()`/`campMidTravel()` interrupting an active trip (see [travel-and-map.md](travel-and-map.md)) pass a real `destId`/`destName`/`partialHours`.
- **Standalone**: the "MAKE CAMP" button fixed on the map (`#camp-here-btn`, stacked above the FIND ME recenter button) calls `showCampView(null, null, 0)` directly — lets the player camp anywhere, anytime, without an active journey (including right where they're already standing in a settlement, if they'd rather sleep rough than pay for the Inn). `#camp-here-btn` hides itself automatically while `#travel-controls` is showing (`showTravelControls`/`hideTravelControls` toggle both), since interrupting an active journey already has its own Stop/Set Up Camp path.

Visual side is always a fixed campfire SVG (`CAMP_ART`), no tier variation since it's not a real place. Header text (`loc-sub`) and the visual tier label branch on `standalone` — "Making camp at `${here}`" vs. "On the road to `${destName}` — `formatDuration(partialHours)` passed", where `here` is `getCurrentDisplayName()`.

Actions (the "Continue" button only renders `${standalone ? '' : ...}` — omitted entirely in standalone mode, since there's nothing to resume):
- **Rest Until Morning**: rolls `NIGHT_AMBUSH_CHANCE` (0.15), reduced to `× BEDROLL_AMBUSH_MULT` (0.85) whenever a Bedroll is carried, first — see [combat.md](combat.md) for why this one can trigger a fight and the Tavern's rest can't. Either way, `finishRest()` (defined inline) calls the same `restFully()` the Tavern uses — full heal plus the same Bedroll stamina-overcap bonus described above, not Hunger/Thirst either — plus `advanceDays(1)`.
- **Continue to `${destName}`** (mid-journey only): closes the overlay and calls `beginTravel(destId)` again — resumes the same journey from `campPos`, recomputing the route fresh. Unlike the old Food-gated system, there's no affordability check to re-run here: Hunger/Thirst simply keep accruing for the remaining leg, with no way for the trip itself to be blocked (see [travel-and-map.md](travel-and-map.md) and [player-state.md](player-state.md)).
- **Choose a Different Destination** / **Back to Map** (label depends on `standalone`): just closes the overlay back to the map. `campPos` (if set) is left untouched either way — the player stays exactly where they stopped/camped, free to tap anywhere else.

## Adding a new location action

All three view functions follow the same pattern: build an array of small metadata objects (or, for Tavern/Market/Blacksmith, just a fixed block of HTML), `.map()` or template them into `#loc-action-list`, then `querySelectorAll` + `addEventListener` to wire clicks. `showMarketPanel` is the template to copy for another shop — `showBlacksmithPanel` is a worked example (see above) — replace `#loc-action-list`'s contents with a new sub-screen rather than adding a new top-level overlay, so the existing "Back" chain of `location-view → sub-panel → location-view → map` stays intact. Work is the exception: not every action needs a sub-panel — a one-shot result like `doWork()` can just run directly from `showLocationView`'s action-list handler and toast the outcome, no `showXPanel`/Back-button pair required. For a pure-flavor sub-panel with no mechanical effect (Temple, Guard House, The Palace), `showFlavorPanel(burgId, title, lines)` is the one to reuse rather than writing a fourth near-identical function — it's already generic over title and line pool.

Gating an action to certain settlement tiers (as Temple/Guard House/Palace do) is just conditionally `.push()`-ing onto the `actions` array in `showLocationView` before it's rendered — `b.tier` is already available there from the burg lookup at the top of the function.
