# Quests (index.html)

Three sources, deliberately different in feel. The **Quest Board** (any settlement) offers several minor, procedurally-generated delivery jobs at once (Deliver a Message, Deliver Cargo). A **Notable Figure** (a handful of specific pinned settlements, not every City/Capital) offers one important kill-task at a time — Deal with the Bandits, or Drive Off the Raiders once their home kingdom is at war — from a named person rather than a board. This split was a deliberate design choice: important quests should come from talking to someone, minor busywork from a board — see [roadmap.md](roadmap.md)'s Talkable NPCs section for how Notable Figure relates to that still-unbuilt idea. A third source, **a companion's personal favor** (see below), was added later — one small, fixed piece of content per recruited companion, offered at the Campfire rather than a settlement.

## Data model

`goblinwar_quests`: a JSON array of accepted quests, default `[]`. Each entry:

```js
{
  id,                    // "q_<timestamp>_<rand>", assigned on accept
  type,                  // "deliver_message" | "deliver_cargo" | "destroy_goblin_nest" |
                          // "protect_caravan" | "train_villagers" | "bounty_variant" |
                          // "kingdom_favor" | "kill_bandits" | "kill_raiders" |
                          // "companion_deliver" | "companion_kill"
                          // ("ask_for_news" is a Board type too, but it never reaches this array
                          // at all — see "The fuller Randomised Bounty Board" below.)
  source,                // "board" | "notable_figure" | "companion"
  giverBurgId, giverName,     // settlement name (board), NPC name (notable_figure), or companion
                               // name (companion) — companion quests have no giverBurgId
  companionId,                // companion source only — which COMPANIONS entry this belongs to
  targetBurgId, targetName,   // deliver_* and companion_deliver only; null for every kill-shaped
                               // type (kill_*, destroy_goblin_nest, protect_caravan, bounty_variant,
                               // kingdom_favor) and train_villagers (tied to the giver's own
                               // settlement instead, read off giverBurgId)
  targetRaces,                 // companion_kill only — which enemyRace(s) satisfy it (see COMPANION_QUESTS)
  targetVariant,                // bounty_variant only — the exact ENEMY_VARIANTS name required
  targetKingdom, tier,          // kingdom_favor only — which kingdom the favor is for, and which
                                 // tier (1 or 2, see getKingdomFavorTier) this specific offer was
  killsRequired, killsProgress, // destroy_goblin_nest only — see "Destroy a Goblin Nest" below;
                                 // killsProgress starts at 0 and only this type is ever paid out
                                 // over more than one matching combat victory
  distanceMiles, distanceHours, // deliver_message/deliver_cargo only; giver-to-target travel
                                 // distance at accept time (see computeDistanceBetween below) —
                                 // undefined for every other type
  reward: { gold, xp, loyalty }, // loyalty only set (and only paid out) for a companion source —
                                  // see "A companion's personal favor" below
  acceptedDay,           // gameDay at accept time, currently unused beyond record-keeping
  status                 // always "active" — a completed quest is removed from the array (see
                          // "Turn-in" below), not marked done; a separate goblinwar_completedQuests
                          // key holds the lightweight history instead, see quests.html below
}
```

Part of every character's save (see [characters.md](characters.md)) like every other `goblinwar_`-prefixed key — `collectCharacterSnapshot()`/`freshCharacterData()`/`applyCharacterData()` all carry `quests` alongside `level`/`xp`/`stats`/`skills`, `completedQuests` (see "Recently Completed" below), and now `companionQuestsCompleted` too (see "A companion's personal favor" below). `killsRequired`/`killsProgress` needed no changes to any of that — the whole `goblinwar_quests` array already round-trips as one opaque JSON string, so a new field on an individual quest object travels for free, same precedent `goblinwar_armies`' own per-army fields already set.

## The Quests tab — quests.html

A dedicated toolbar tab (see [secondary-pages.md](secondary-pages.md)) rather than only ever seeing quests from inside a settlement's Quest Board panel. Two sections: **Active Quests** (every entry from `getActiveQuests()`, each with a **View Location** button — only shown when `q.targetBurgId` is set, i.e. a delivery quest; kill-quests have no single destination, same reasoning `buildQuestMarkers()` already uses — and an **Abandon** button that deletes it from `goblinwar_quests`, `confirm()`-gated same UX as Delete Character, and now has a real cost — see below) and **Recently Completed**, a read-only history off a new `goblinwar_completedQuests` key (newest first, capped at `COMPLETED_QUESTS_MAX` (20) entries via `recordCompletedQuest(q)`, called from both completion sites below right before the quest itself is removed). Abandoning a Notable Figure kill-quest doesn't need any special handling to free its "one active at a time" cap (below) — that cap is checked against live storage every time the panel opens, so removing the quest object frees the slot automatically.

**Real consequences for quest refusal/abandonment — the Expansion Research idea of the same name.** Abandoning used to just delete the quest object with no other bookkeeping — a genuinely free reroll against the Board/Notable Figure's own seeded-offer cadence, and a companion's own personal favor could be walked away from and immediately re-offered at the Campfire for nothing (`getCompanionQuestOffer` only ever excluded an already-*active* quest, not a previously-abandoned one — abandoning cleared that exclusion for free). `abandonQuest(id)` (quests.html) now branches on `q.source`: a `'companion'` quest costs that companion loyalty (`QUEST_ABANDON_LOYALTY_PENALTY`, -15, via a duplicated `adjustCompanionLoyalty` — can cost the companion outright the same way any other loyalty hit can); a `'board'` or `'notable_figure'` quest costs reputation with `q.giverKingdom` (`QUEST_ABANDON_REP_PENALTY` -10 for an impersonal Board job, `QUEST_ABANDON_REP_PENALTY_FIGURE` -18 for breaking a promise made to a named person — worse). `giverKingdom` is a new field stamped onto the quest object **at accept time** by index.html's own two accept handlers (`getControllerKingdom(giverBurgId)`/`getControllerKingdom(figure.homeBurgId)`), specifically because quests.html never loads the graph (see below) and has no other way to resolve "which kingdom" when Abandon is actually clicked. Scoped to abandonment only, not a separate "refusal" action — there's no decline button anywhere in the game that leaves any trace to react to (not accepting a Notable Figure's offer, for instance, writes nothing at all), so abandoning an already-accepted quest is the one point with real persisted state worth a real consequence.

**Reputation and companion-loyalty machinery is duplicated into quests.html for this** (`REPUTATION_KEY`/`adjustReputation`/`reputationLabel`/`updateRenownTitle`/`PARTY_KEY`/`LOYALTY_KEY`/`adjustCompanionLoyalty`), same no-modules convention as `questTitle`/`questDesc` above — none of it needs the world graph, just plain `localStorage` reads/writes, so it duplicates cleanly without pulling `generateWorld()` in. Fixed two points of drift in `questTitle`/`questDesc` while touching them for this: quests.html's copies were missing the `companion_kill`/`companion_deliver` branches entirely (a pre-existing bug — Abandon's own confirm dialog would've shown "Abandon \"Quest\"?" for a companion's personal favor) and the kingdom-specific "Drive Off X's Raiders" wording from "Kingdom-specific kill quests" above. A small `COMPANION_QUESTS` catalog (title/ask text only) was added to quests.html to back the companion branch.

**View Location** hands off to index.html rather than centering anything itself — quests.html never loads `travel-graph.json` (see below), so it can't. Clicking it navigates to `index.html?viewBurg=<targetBurgId>` (cache-busted, same convention as every other internal link — see [CLAUDE.md](../CLAUDE.md)); index.html's own load sequence checks that param and, if set, calls `viewLocation(burgId)` instead of the normal "recenter on where you actually are" logic. `viewLocation(burgId)` (index.html, also used by the Quest Board's offer cards below) closes whatever settlement panel is open, centers/zooms the map on that burg — the same target the FIND ME button (`#recenter-btn`) uses — and opens its info-card via `onMapTap(burgId)`, exactly as if the player had tapped it directly (name, tier, population, and a working Travel Here button).

The map itself also marks every active delivery quest's destination: `buildQuestMarkers()` (index.html) draws a small gold flag above any settlement that's the `targetBurgId` of an active `deliver_message`/`deliver_cargo` quest, rebuilt (like `buildFrontlineMarkers`) on load and after any accept/turn-in/abandon that changes the active quest list. Kill-quests never get a marker — they complete on the next matching combat victory *anywhere*, not by visiting a place, so there's no single location to mark.

## Offers aren't stored — they're regenerated

Neither the Quest Board's offers nor the Notable Figure's offer are ever written to `localStorage`. `generateNotableFigureOffer(burgId)` regenerates fresh on every panel open, seeded deterministically from the figure's name + the current `gameDay`. `generateBoardOffers(burgId)` regenerates too, but seeded off a **month index** (`getBoardMonthIndex()`, `Math.floor(gameDay / DAYS_PER_MONTH)`) rather than `gameDay` directly — per the project owner, the Board resets once a real in-game month, not once a day. Reopening the same settlement's panel within the same month shows the same offers; once the month index advances, they reroll. This is the same reasoning as Work's per-day cooldown (see [locations-and-camp.md](locations-and-camp.md)) — reuse the calendar as the "has this refreshed yet" signal instead of inventing separate storage, just on a longer cycle for the Board.

`hashSeed(str)` folds a string into a 32-bit int; `seededRandom(seed)` (mulberry32) turns that into a `[0,1)` float. Neither needs to be cryptographically strong — this is flavor generation, not anything security-relevant.

## The Quest Board — `showQuestBoardPanel(burgId)`

A fifth entry in every settlement's action list (alongside Tavern/Marketplace/Work/Talk to Townsfolk — see [locations-and-camp.md](locations-and-camp.md)), same `#loc-action-list`-replacement pattern as Market/Tavern/flavor panels.

- **Your Active Quests** — every quest in `getActiveQuests()`, regardless of source or which settlement it was given at. quests.html (above) is now the dedicated place to see and manage everything outstanding, but the Board still shows this same list too, so accepting and reviewing stays in one screen without a trip to another page. This mini list doesn't get its own View Location button — it's the same data quests.html already shows with one, and the player's already standing in a settlement's action menu here, not the map.
- **On the Board** — `generateBoardOffers(burgId)` returns up to `getBoardQuestCount(burgId)` offers this month: a settlement's tier caps how many it can *ever* show at once (`BOARD_MAX_QUESTS_BY_TIER`: village 1, town 2, city 2, capital 3), and the actual count for the current month is itself a seeded roll from 0 up to that cap inclusive — a village doesn't necessarily have its one possible job posted every month. Each slot independently rolls which *type* it is from a small weighted pool (`getBoardTypeWeights`/`pickWeightedBoardType` — see "The fuller Randomised Bounty Board" below) rather than a fixed coin flip: delivery (then split the original way between **Deliver a Message** and the heavier-paying **Deliver Cargo**, both the same `deliver_*` mechanic underneath — see Turn-in below) is the common case, with **Destroy a Goblin Nest**, **Bounty: &lt;variant&gt;**, **Protect a Caravan**, **Train the Villagers**, **Ask Around for News**, and (only once eligible) **A Favor for &lt;Kingdom&gt;** filling out the rest. An offer already matching an active quest (same type + giver, plus target for a delivery type) is filtered out so accepting one doesn't leave a visible duplicate the same month. Every delivery offer card also gets a **View Location** button (`viewLocation(o.targetBurgId)`, see quests.html above) next to Accept; every other type has no `targetBurgId` (most pay out on a kill anywhere, like the Notable Figure's own kill-quests below) so its card omits that button, same `o.targetBurgId ?` check quests.html's Active Quests list already uses.
- **Targets exclude enemy territory.** Per the project owner, delivering into a settlement actively hostile to the giver doesn't make sense — `isEnemyTerritory(giverBurgId, targetBurgId)` compares each side's *alliance* (`ALLIANCE[getController(...)]`, Good vs. Bad — see [factions-and-territory.md](factions-and-territory.md)), not their specific kingdom, so a target is only excluded when it's actually on the opposite side of the war, not merely a different kingdom on the same side. A 'neutral'-controlled burg (no alliance either way) is never excluded.
- **Reward scales with real travel distance.** `computeDistanceBetween(giverBurgId, targetBurgId)` (index.html, near `computeTravel`/`routeBetween` in the travel code — see [travel-and-map.md](travel-and-map.md)) routes between the two settlements the same way live travel does, independent of where the player actually is right now. The resulting `hours` adds `DISTANCE_GOLD_PER_HOUR` (0.5) gold and `DISTANCE_XP_PER_HOUR` (0.3) XP per hour on top of the existing base+random roll (`10-25` gold Deliver a Message / `15-30` gold Deliver Cargo, `8-20` XP either way before the distance bonus) — a courier run across half the map pays noticeably better than one to the next settlement over. `distanceMiles`/`distanceHours` are recorded on both the offer and the accepted quest object so the distance never needs recomputing later (quests.html in particular never loads the graph at all).
- **Travel time is shown next to the quest.** `questDesc(q)` appends `questDistanceNote(q)` — `` (`${formatDuration(q.distanceHours)} away`) `` — to a delivery quest's description, both as a Board offer and once accepted, using the exact same `formatDuration` travel's own UI uses (see [travel-and-map.md](travel-and-map.md)).
- Accepting pushes a real quest object (with a fresh `id`, `acceptedDay: gameDay`, `status:'active'`) onto `goblinwar_quests`, calls `buildQuestMarkers()`/`refreshQuestBadge()` (see quests.html above) so the map and toolbar reflect it immediately, and re-renders the panel.

## The fuller Randomised Bounty Board

Per the tracker's own brainstormed idea of that name (see [roadmap.md](roadmap.md)'s Quests section). The Board used to pick a slot's type with a fixed 1-in-3 roll for Destroy a Goblin Nest, else a coin flip between the two delivery types — real but narrow. `getBoardTypeWeights(controllerKingdom)` returns a small weighted list instead (`[{type, weight}, ...]`), and `pickWeightedBoardType(weights, roll01)` turns one `seededRandom` roll into a pick (walk the list subtracting each `weight` from the scaled roll until it goes negative) — the same deterministic-per-slot seeding every other Board roll already uses, just feeding a bucket pick instead of a boolean. Delivery keeps the largest weight (5 of 11 ordinarily) since courier work is still the Board's bread and butter; Destroy a Goblin Nest keeps a bigger share (2) than the five newer types (1 apiece) as the more established "regular" kill job. `kingdom_favor` only enters the list at all once `isKingdomFavorEligible` says yes (see below) — its presence, not just its odds, reacts to real standing. Adding a sixth or seventh type later is one more entry in that list plus a new branch in `generateBoardOffers`'s own if-chain, same shape every entry below already follows.

- **Protect a Caravan.** `{type:'protect_caravan', source:'board'}`, no `targetBurgId`. Doesn't fit the delivery or kill family's existing completion shapes at all — it's not won by arriving anywhere, and it's not won by killing a specific race or variant either, just by surviving whatever hits the caravan. Completes on the player's very next **ambush** victory (`endCombat`, checked ahead of `questMatchesRace` the same way `destroy_goblin_nest` is) — any race, road or camp — via a new `combat.isAmbush` flag `triggerAmbushFight` sets right where it's the only place an ambush fight is actually started, captured into a local `isAmbush` at the top of `endCombat` the same way `enemyRace`/`attackerKingdom` already are. A siege defense, a Notable Figure's bounty kill, a field-battle clash — none of those set the flag, so only a genuine road/camp ambush ever completes it, matching "you were hired to guard **this** caravan on **this** road," not "you won some fight somewhere."
- **Train the Villagers.** `{type:'train_villagers', source:'board'}`, no `targetBurgId` either — but unlike every other type, it's tied to the *giver's own* settlement rather than somewhere else or anywhere. Completes the next time the player does a day's Work there (`doWork(burgId)`, checked right after the ordinary Work payout, before its own toast is shown) — "drilling the militia instead of odd jobs" is a one-line addition to an action that already exists, needing no new mechanism at all. Reputation gain is `REP_GAIN_MINOR`, same as an ordinary delivery, since it's a modest in-town favor rather than a kill-sized task.
- **Ask Around for News.** `{type:'ask_for_news', source:'board'}`, no `targetBurgId`, and — unique among every quest type in this file — **it never joins `goblinwar_quests` at all**. Accepting it pays out immediately, in the same click, in `showQuestBoardPanel`'s own `data-offer` handler (checked before the normal push-onto-`goblinwar_quests` path every other type falls through to): gold/XP via `setGold`/`addXp`, a real line picked from `getTownsfolkLines(burgId)` — the exact same reactive flavor pool Talk to Townsfolk already draws from, not a separate hand-written pool — shown as "the news" in the toast, and `recordCompletedQuest(offer)` so quests.html's Recently Completed history shows it like anything else even though it never sat in the active list. Rolls fresh every month with everything else on the Board; there's no "already active" guard to write since nothing stays active.
- **Bounty: &lt;variant&gt;.** `{type:'bounty_variant', source:'board', targetVariant}` — the one new type that completes through `questMatchesRace` without needing its own branch in `endCombat`'s `forEach`, since "match by this exact enemy name" is still a single-victory completion, just keyed off `enemies.some(e => e.name === q.targetVariant)` instead of `enemyRace`. `targetVariant` is picked from `BOUNTY_VARIANT_NAMES` — the handful of already-existing `ENEMY_VARIANTS` entries that read as a real "boss" (every `smart:true` one, plus the wildlife apex predator Dire Bear) rather than a hand-authored second roster. Reward is derived from that exact variant's own `goldRange`/`xpRange` (its midpoint) times `BOUNTY_REWARD_MULT` (2.5) — retuning a variant's own stats elsewhere automatically retunes its bounty too, nothing to keep in sync by hand. Doesn't force that variant to spawn; ambush composition is still whatever `pickWeightedVariant`/`getAmbushToughnessBias` already rolls (see [combat.md](combat.md)) — a bounty is a reason to go hunting, not a guarantee of a kill, a deliberate scope cut flagged here rather than hidden.
- **A Favor for a Kingdom.** `{type:'kingdom_favor', source:'board', targetKingdom, tier}` — the "Faction Reputation Chain" roadmap idea: a kingdom you've built real standing with eventually asks a bigger favor of its own, tiered on that same reputation number rather than a separate progress stat. `isKingdomFavorEligible(kingdom)` (near `generateBoardOffers`) gates it: tier 1 needs Friendly+ reputation, tier 2 (bigger reward, `35*tier` gold base instead of flat) only once Trusted — reusing `reputationLabel`'s own existing boundaries rather than inventing new thresholds. **The capstone tier 3** (added in a later pass, closing the roadmap's own "a third tier past the cap of 2" gap) has no higher `reputationLabel` bucket to reuse — Trusted is already the top one, capped at 100 — so it's gated on a raw reputation number instead (`KINGDOM_FAVOR_TIER3_REP`, 80) rather than inventing a new label. It stops offering entirely once `KINGDOM_FAVOR_MAX_TIER` (3) is reached, and both `questTitle`/`questDesc` (index.html and quests.html's duplicate) give it distinct "A Lasting Alliance with X" framing instead of the ordinary "A Favor for X" wording, so reaching it reads as a real capstone rather than just another number. Completes exactly like Drive Off the Raiders (any goblin/ork kill, anywhere — added as one more clause in `questMatchesRace`, no new branch needed) but pays bigger reputation (`REP_GAIN_MAJOR` instead of `REP_GAIN_MEDIUM`) and calls `recordKingdomFavorCompleted(targetKingdom)` on completion, advancing the tier that's what later unlocks the next one — the actual "chain": completing one favor is what makes the next, better one possible. `goblinwar_kingdomFavorTier` (`{kingdomName: tiersCompleted}`, sparse) is a genuinely new top-level key, unlike `killsRequired`/`killsProgress` above which just ride along inside `goblinwar_quests` — see [factions-and-territory.md](factions-and-territory.md)'s character-save-key list for where it's triplicated (index.html, settings.html, characters.html).

## The Notable Figure — `showNotableFigurePanel(burgId)`

`NOTABLE_FIGURES` is a small fixed roster of `{id, name, title, homeBurgId, portrait?}` — each figure now has their own multiple-choice conversation tree too (`NOTABLE_FIGURE_TREES`, a Talk button in `showNotableFigurePanel` separate from and always available alongside the quest offer below — see [roadmap.md](roadmap.md)'s "Conversations are multiple choice now"), on top of the quest-offer flow this file is actually about. Unlike the Board, **each figure is pinned to one real settlement and doesn't move** — a deliberate project-owner call: important quests should come from a specific person in a specific place, not get randomly reassigned to a different city every day the way the Board's offers regenerate. All five currently sit in Good-alliance (human/dwarf) territory to match their names: Captain Aldric Vane (Bary), Yselle Thorn (Yeone), Elder Bram Oswick (Mosver), Scoutmaster Priska Ren (Sodoy), Sir Corwin Hale (Stothers).

All five are cataloged in the "Character Forge" tracker artifact (see [roadmap.md](roadmap.md)'s Talkable NPCs section for the link), and all five now have real portrait art wired all the way into the game via a `portrait` field on their `NOTABLE_FIGURES` entry (`assets/figures/<slug>.png`). While `showNotableFigurePanel` is open, the figure's portrait is overlaid on the settlement's own banner art via `#loc-banner-portrait` (see [locations-and-camp.md](locations-and-camp.md)) — the figure appears on the same backdrop the player just walked into, rather than in a disconnected panel.

`getFigureForBurg(burgId)` is the single source of truth for "is there a figure here right now": it looks up whether `burgId` is anyone's `homeBurgId`, then checks `getController(homeBurgId) !== home.race` (see [factions-and-territory.md](factions-and-territory.md)) — if their home has been captured by another race since, it returns `null`. **This is the "they disappear if their city falls" behavior the project owner asked for**: the Notable Figure action itself stops appearing in `showLocationView`'s action list for that settlement (via the same `getFigureForBurg` check), and opening the panel anyway (a stale render from before a capture) shows "This place has changed hands. Whoever once sought your help here is gone." instead of an offer.

An already-*accepted* kill-quest is unaffected if the giver's city falls afterward — the reward was already promised, and turn-in (below) doesn't require revisiting the giver's panel at all. Only *new* offers stop once a figure is gone.

**Which task a figure offers reacts to real game state, not randomness.** `generateNotableFigureOffer(burgId)` checks `isAtWarAt(figure.homeBurgId)` (see [factions-and-territory.md](factions-and-territory.md)): at peace, the offer is Deal with the Bandits (`20-40` gold / `18-30` XP); once that figure's home kingdom is at war, the offer becomes Drive Off the Raiders instead — the actual Goblin War threat, paying more (`35-60` gold / `25-45` XP) to reflect the bigger danger. Same reactive-world spirit as Marketplace pricing and `pickAmbushEnemy` (see [combat.md](combat.md)) already reacting to war state. The reward is seeded from the figure's name + `gameDay`, not from `burgId` — the figure IS the settlement here, so no separate seed is needed.

**Capped at one active Notable Figure quest globally**, regardless of which figure gave it. The panel checks `getActiveQuests().find(q => q.source === 'notable_figure')` — by `source`, not `type`, so the cap still holds once a second important quest type exists — and if one's already active from a *different* figure, shows "You already have a task in progress for X" instead of a new offer. If it's active from *this* figure, shows that quest's status instead. This is deliberate: these are meant to feel like a real ask from a real person, not a stack of odd jobs like the Board.

**Kingdom-specific kill quests — the Expansion Research idea of the same name.** Drive Off the Raiders used to just want any goblin or ork kill, anywhere — `attackerKingdom` was already tracked on a siege's own Defend the Walls fight (`combat.attackerKingdom`, see [combat.md](combat.md)) but nothing checked it against a quest. `generateNotableFigureOffer` now also picks a `targetKingdom`: one of the figure's home kingdom's own current Bad-alliance enemies at war (`getEnemiesAtWar`), seeded the same deterministic way as the reward numbers. `pickAmbushEnemy` (see [combat.md](combat.md)) picks a specific attacking kingdom the same way for an ordinary raiding-party ambush now too, not just a siege defense, so either source of a kill can satisfy a kingdom-specific quest. `questTitle`/`questDesc` show the named kingdom ("Drive Off Krazgak's Raiders") when `targetKingdom` is set, and `endCombat`'s race-match check additionally requires `q.targetKingdom === combat.attackerKingdom` for that quest to pay out. A quest with no `targetKingdom` (no real enemy to name at accept time, or an older save) keeps the old any-raider-anywhere behavior — this is additive, not a breaking change to the type.

**Accepted quests react to the live war tick — the Expansion Research idea of the same name.** The task above was previously frozen to whatever `isAtWarAt` returned *at accept time* — a Deal with the Bandits quest accepted at peace stayed a bandit quest even if that kingdom went to war the very next week, and vice versa. `reconcileQuestsWithWarState()` (index.html) runs once per weekly tick, from the tail of `runFactionAITick` right after that week's declare/peace pass has settled every relation, and re-checks every active `notable_figure` kill-quest's `type` against the giver's *current* war state — flipping `kill_bandits`↔`kill_raiders` in place when it's stale, with a `recordWorldEvent` line (not a toast — this rides the same Chronicle-feeding event log settlement captures and peace treaties already write to, see [factions-and-territory.md](factions-and-territory.md)) marking the shift either way. Because `questTitle`/`questDesc`/`endCombat`'s race-match check all read `q.type` live, flipping that one field is the only change needed — everywhere the quest is shown (quests.html, the Quest Board's mini-list, the Notable Figure panel) picks it up automatically. The same pass also keeps `targetKingdom` honest: if the specific kingdom a kill_raiders quest named makes its own separate peace while the figure's home kingdom stays at war with someone else, the quest is repointed at a current enemy (with its own world-event line) rather than demanding a kill from a kingdom that's no longer fighting anyone.

## A companion's personal favor — a third source

Per the project owner's roadmap note: one small personal quest per recruited companion, reusing the existing Deliver/Kill turn-in architecture rather than inventing a third completion mechanism — exactly the "mostly a new offer-generator, not new architecture" pattern this file's own "Adding a new quest type" section already describes. `COMPANION_QUESTS` (index.html, right after the `COMPANIONS` catalog) is fixed, one-time content, not seeded/randomized: one entry per companion id, `{type: 'companion_kill'|'companion_deliver', targetRaces?, targetBurgId?, title, ask, gold, xp}`. Unlike the Board or a Notable Figure, this isn't capped globally — each recruited companion can have their own personal quest active at once (up to 3, one per party slot), since each is a distinct relationship, not a shared civic quest-giver.

- **Where it's offered.** At the Campfire (`showCampfirePanel`, see [travel-and-map.md](travel-and-map.md)'s Camp write-up), since that's already the one place a recruited companion is a real individual rather than a roster entry, not a settlement panel. `getCompanionQuestOffer(id)` returns the companion's `COMPANION_QUESTS` entry only when it hasn't already been completed (`getCompanionQuestsCompleted()`, a small persisted `goblinwar_companionQuestsCompleted` array of companion ids — checked directly rather than via the capped/trimmed `goblinwar_completedQuests` history, so a long-lived character can't have an old personal quest re-offered once its record eventually rolls off that 20-entry cap) and isn't already active for that companion. Rendered as its own offer card beneath that companion's "Talk to X" row — an Accept button if there's something to offer, an in-progress summary (`questTitle`/`questDesc`) if already accepted, nothing at all once it's done.
- **`companion_kill`** reuses the exact same `endCombat` victory-matching block Notable Figure kill-quests use, extended with one more condition: `q.targetRaces.includes(enemyRace)` (each companion's own quest carries its own target race list, rather than being keyed to a fixed `type`→race table the way `kill_bandits`/`kill_raiders` are, since different companions want different things — Ser Brannoc Ward wants ork/goblin raiders avenging his old mentor, Thrain Emberforge wants bandits off the trade road his forge depended on). Since a companion quest can be active *alongside* a Notable Figure one, this block now resolves every matching active quest off a single kill, not just the first — previously safe to short-circuit only because a Notable Figure quest was always the sole thing that could ever match.
- **`companion_deliver`** (Wren Sable — carry a letter back to her own `homeBurgId`) was added to `DELIVERY_QUEST_TYPES` verbatim, so it completes on arrival exactly like Deliver a Message/Deliver Cargo, shows up in `buildQuestMarkers()`'s map flags, and renders in quests.html's Active Quests / the Quest Board's own mini-list for free — no extra UI needed anywhere, since all of those already key off `getActiveQuests()`/`DELIVERY_QUEST_TYPES` generically.
- **The payoff is different on purpose.** Every other quest type pays gold/XP plus a reputation nudge with a kingdom. A companion's personal favor pays gold/XP plus `adjustCompanionLoyalty(companionId, COMPANION_QUEST_LOYALTY_GAIN)` instead (20 — bigger than any single existing loyalty-moving action, deliberately: this is meant to read as the single biggest positive personal moment with that companion, the same weighting spirit Incite War's `INCITE_WAR_LOYALTY_PENALTY` gives the single biggest negative one) — no reputation nudge at all, since a personal favor for a companion isn't a kingdom-facing act.

## Destroy a Goblin Nest — a counted kill quest, the Board's first non-delivery type

Per the tracker's brainstormed idea of the same name (see [roadmap.md](roadmap.md)'s Quests section). Every kill-type quest before this one — Deal with the Bandits, Drive Off the Raiders, a companion's `companion_kill` — pays out on the very next matching combat victory, full stop. A single-kill bounty doesn't read as "a nest" though, so this one needed a genuinely different completion shape: it names a `killsRequired` (3-5, rolled at offer time) and tracks `killsProgress` (starts at 0 once accepted) against it, only paying out once the count's actually met.

- **Offered from the Board**, not a Notable Figure — it's meant to read as one more minor posted job, not an important ask from a named person, and Notable Figure's own one-active-globally cap and war-reactive bandit/raider toggle don't fit a fixed-target kill count anyway. `generateBoardOffers` rolls a 1-in-3 chance of this type per slot *before* the existing deliver_message/deliver_cargo coin flip, so it's additive — that coin flip's own seed and odds are untouched. No `targetBurgId` at all (same as a Notable Figure's kill-quests), so it skips the View Location button and the distance-based reward bonus; reward instead scales off `killsRequired` itself (`20 + killsRequired*10` gold, `12 + killsRequired*6` XP, plus a small random roll on each) — first-pass balance numbers, same "not verified against real play" caveat as every other reward formula in this file.
- **Turn-in lives inside `endCombat`'s existing kill-matching block**, not a new function — a `destroy_goblin_nest` quest is checked *before* `questMatchesRace` (which has no branch for it) rather than through it, since its condition genuinely differs: on a goblin-race victory, every enemy killed in that one fight (`enemies.length`, not just 1 — a multi-enemy raiding-party kill can clear several goblins toward the count at once) adds to `killsProgress`; only once `killsProgress >= killsRequired` does it join the `rewarded` list and get removed/paid out exactly like every other kill quest. Short of that, it stays in `remaining` with its new `killsProgress` saved, and a progress line ("3 of 5 goblins slain for Bary's nest") folds into the same combined victory toast the completed quests' own lines already build — the player never gets a separate popup for a kill that only moved the needle. `questDesc(q)` shows the same "`X` of `Y` goblins slain" phrasing both before accepting (reading the offer's own `killsRequired` with `killsProgress` undefined → shown as 0) and after, in quests.html, the Quest Board's own mini-list, and the toast line alike — one piece of text, every place it's shown.
- **Reputation payout, same as any other kill quest.** It falls into `endCombat`'s existing non-companion `else` branch on completion, crediting the giver settlement's controller `REP_GAIN_MEDIUM` reputation — the same amount a Notable Figure kill-quest pays, since clearing an entire nest is comparable effort even though it's Board-sourced.
- **Abandoning** needs no new handling at all: quests.html's `abandonQuest` already branches on `q.source`, not `q.type`, and this type's source is `'board'` — the existing `QUEST_ABANDON_REP_PENALTY` path (and the `giverKingdom` already stamped onto the quest object at accept time, same as every other Board offer) covers it for free.

## Turn-in

Four different mechanisms now, because completion conditions genuinely differ enough that forcing everything into "deliver" or "kill" stopped making sense once Protect a Caravan, Train the Villagers, and Ask Around for News joined the roster:

- **Deliver a Message / Deliver Cargo / a companion's `companion_deliver`** all complete on arrival, identically. `checkQuestTurnIns(burgId)` runs at the very top of `showLocationView`, before anything else renders — so it fires whether the player just arrived via travel, is re-entering a settlement they're standing in, or backed out of a sub-panel. It scans `goblinwar_quests` for any active quest whose `type` is in `DELIVERY_QUEST_TYPES` (`['deliver_message', 'deliver_cargo', 'companion_deliver']`) and whose `targetBurgId` matches, pays out `setGold`/`addXp`, then branches on `q.source`: a companion quest marks itself completed (`markCompanionQuestCompleted`) and pays loyalty (`adjustCompanionLoyalty`) instead of the Board/Notable Figure branch's reputation nudge (`adjustReputation`) — see "A companion's personal favor" above. Records it either way (`recordCompletedQuest(q)`, see quests.html above) and removes it, then calls `buildQuestMarkers()`/`refreshQuestBadge()` if anything actually completed. Safe to call on every `showLocationView` invocation (which happens a lot) since a completed quest is gone from storage immediately — there's nothing left to complete twice.
- **Deal with the Bandits / Drive Off the Raiders / a companion's `companion_kill` / A Favor for a Kingdom / Bounty: &lt;variant&gt;** all complete on the next matching combat victory *anywhere*, not just near where the quest was accepted. `endCombat('victory')` (see [combat.md](combat.md)) checks `combat.race`/`combat.enemies` — `race` is threaded through `startCombat`/`triggerEnemyFight` alongside the existing `enemyName`/`goldRewardRange`/`xpRewardRange` specifically so this check is possible — against a small `questMatchesRace(q)` helper (`kill_bandits` wants `'bandit'`; `kill_raiders`/`kingdom_favor` want `'goblin'` or `'ork'`; `companion_kill` wants whatever's in that specific quest's own `targetRaces`; `bounty_variant` wants a specific enemy *name* in that fight's `enemies` array, not a race at all). Every matching active quest is paid out and folded into the same victory toast (one message, not several competing `showToast` calls), each recorded (`recordCompletedQuest`) and the badge refreshed once at the end — since more than one of these can now be active at once (a companion quest alongside the one Notable Figure quest the global cap still allows, or either alongside a Board-sourced favor/bounty), this resolves every match off a single kill rather than stopping at the first. A companion branch marks itself completed and pays loyalty the same way the delivery side does; `kingdom_favor` pays bigger reputation and advances its own tier (see above) instead of the usual medium amount.
- **Destroy a Goblin Nest / Protect a Caravan** complete inside that same `endCombat` block, but checked *ahead of* `questMatchesRace` rather than through it, since neither's condition is a simple race/name match: a nest needs several victories' worth of kills counted up (`killsProgress` vs. `killsRequired`, see its own section above) before it pays out at all; a caravan needs the win to specifically be an *ambush* (`combat.isAmbush`, set only where `triggerAmbushFight` actually starts one), not any combat victory anywhere.
- **Train the Villagers / Ask Around for News** don't go through `endCombat` or `checkQuestTurnIns` at all — see their own sections above. Training completes inside `doWork(burgId)`, Work's own existing handler, the moment the player works a day at the giver's settlement; Asking for News never becomes an active quest in the first place; it resolves instantly in the Accept click itself.

## Adding a new quest type

A new type is still mostly a new offer-generator + a new turn-in check, not new architecture, even past four source categories and four completion mechanisms — every addition since the original Deliver/Kill split has been "one more condition somewhere that already exists," never a rewrite:

1. Pick a `type` id and add its copy to `questTitle()`/`questDesc()` (both index.html and quests.html's own duplicate copy — see the no-modules convention in [CLAUDE.md](../CLAUDE.md)).
2. Decide Board (minor, several at once, generic — see `getBoardTypeWeights` for adding a new weighted bucket), Notable Figure (important, one at a time, named, reacts to whether the figure's home is at war), or Companion (personal, one per recruited companion, fixed one-time content rather than seeded/regenerated) — or a fourth source later, if one ever makes sense.
3. Write a `generate*Offer(s)` function following the seeded-PRNG pattern above (or, for fixed content like a companion's, a plain catalog lookup), and an Accept handler that pushes the finished quest shape onto `goblinwar_quests` — or, if it should resolve the instant it's accepted like Ask Around for News, pays out right there instead of ever pushing one.
4. Decide which completion mechanism fits: `DELIVERY_QUEST_TYPES` (arrival) or a new clause in `questMatchesRace` (a single matching kill, by race or by exact name) if it's delivery- or kill-shaped; a new condition checked *ahead of* `questMatchesRace` in the same `endCombat` block if the condition needs its own running state (a kill count, a flag like "was this an ambush") but still hangs off combat; or, if it doesn't involve combat or arrival at all, hook an existing action that already fires at the right moment (Train the Villagers piggybacks on `doWork`) rather than inventing a whole new trigger.

Every quest idea the tracker originally brainstormed now has at least a first slice built — Protect a Caravan, Train Villagers, Ask for News, a Faction Reputation Chain (now 3 tiers deep, not just 2), and a fuller Randomised Bounty Board are all covered above. See [roadmap.md](roadmap.md)'s Quests section for what's still open beyond these first slices (more Bounty Board variants, etc.) — none of it needs new architecture either, per the pattern above.
