# Roadmap: Stubs Already Scaffolded in the Code

Every "coming soon" placeholder currently in the game, collected in one place so future work has a checklist instead of needing to grep for it. Each entry names the exact file/element so implementing it means replacing that stub, not guessing where it should live.

## Skills & Progression — character.html — in progress

**Built so far:** the whole loop is real. Combat victories grant XP (`ENEMY_VARIANTS`' `xpRange`, rolled in `endCombat`), leveling up grants a skill point plus a small Health/Stamina bump, and character.html lets a player spend each point on Strength/Agility/Intelligence, one of 9 passive perks, or one of 6 active special attacks — all sharing the same `goblinwar_skills` unlock storage and stat-threshold gating. The active moves show up as a "Specials" button in combat (`#combat-specials-panel`, `combatSpecial()` in index.html) alongside Attack/Flee, each usable once per fight. See [player-state.md](player-state.md)'s "Leveling & stats" for exactly where every perk and move hooks in.

The former naming collision is resolved: the active move is "Crushing Blow" (2x damage), distinct from the passive "Power Strike" perk (+2 flat damage, always on).

**Not built yet:** nothing — multi-enemy encounters (see below) closed the last gap here.

**Data model:** five new `localStorage` keys (see [player-state.md](player-state.md) once added) — `goblinwar_level` (default `1`), `goblinwar_xp` (default `0`), `goblinwar_skillPoints` (unspent points, default `0`), `goblinwar_stats` (`{str, agi, int}`, default all `0`), `goblinwar_skills` (`{skillId: true}` for unlocked perks/moves, default `{}`). All five need adding to the character snapshot shape in all three duplicated spots (index.html, settings.html, characters.html — see [characters.md](characters.md)) or leveling resets on save/switch.

XP curve: roughly `xpForLevel(n) = 40 * n^1.5`. Each `ENEMY_VARIANTS` entry (see [combat.md](combat.md)) gets an `xpReward` field alongside its existing `goldRange`, rolled in `endCombat('victory')` the same way gold is. Leveling up grants 1 skill point plus a small flat bump to `maxHealth`/`maxStamina` (e.g. +8/+4), so it feels good even before a point is spent.

**Passive perks** (spend a skill point, gated on a stat threshold so raw stats and perks stay entangled): Power Strike (Str, +2 flat dmg), Pack Mule (Str, +10 carry capacity — see `CARRY_CAPACITY` in [player-state.md](player-state.md)), Iron Skin (Str, −1 flat dmg taken), Evasion (Agi, 15% chance to fully dodge the enemy counter-attack in `combatAttack()`), Second Wind (Agi, 25% chance an attack costs no stamina), Sure Feet (Agi, −10% ambush chance, see `AMBUSH_CHANCE_PER_DAY`/`rollAmbush()` in [combat.md](combat.md)), Silver Tongue (Int, −10% Marketplace buy prices), Scavenger (Int, +20% gold from victories), Field Rations (Int, −10% Hunger/Thirst gained from travel/waiting, see `hoursToHungerGain()`/`hoursToThirstGain()` in [player-state.md](player-state.md)).

**Active special attacks** — built. Combat no longer stays "just hit Attack": a "Specials" button opens `#combat-specials-panel`, listing whichever of the 6 moves are unlocked, each costing more stamina than a basic Attack and usable once per fight (`combat.usedMoves`, reset in `startCombat`): Crushing Blow (Str, 2x damage to your target), Reckless Swing (Str, 2.5x damage to your target, but that one enemy's counter ignores armor *and* Evasion — see "Multi-enemy encounters" below for why it's scoped to just that enemy), Precise Shot (Agi — since the game has no miss chance to guarantee against, this instead always rolls max damage rather than random), Adrenaline Rush (Agi, a free extra attack with no stamina cost), War Cry (Int, cuts *every* enemy's damage 30% for the rest of the fight, deals no damage itself), Cleave (Str, higher tier — hits every alive enemy for 60% damage each).

**Multi-enemy encounters — built.** Goblin/Ork raiding-party ambushes now spawn 2-3 enemies at once (Bandit ambushes stay solo); `combat.enemies` is an array with click-to-target UI (`#combat-enemies`, `renderEnemies()`), a per-enemy HP bar, auto-retargeting off a killed enemy, and every alive enemy countering each round (`runEnemyCounters`) — the actual difficulty lever that makes a raid harder than a solo fight, not just longer. See [combat.md](combat.md)'s "Multi-enemy encounters" section for the full mechanics and the balance calls made (War Cry/Cleave hit every enemy; Reckless Swing's ignore-armor counter is scoped to only its one target).

**Still deliberately not part of this build:**
- **Talkable NPCs / dialogue** — already captured below as an unscoped idea; explicitly parked, unrelated system (NPC data model, conversation UI, settlement hooks).

**Moved off character.html onto a new "Skills" tab — done.** Per the project owner: Strength/Agility/Intelligence, the 9 perks, and the 6 special attacks now live on [skills.html](secondary-pages.md), a new top-level nav destination on index.html's toolbar alongside Inventory/Party/Hero/Settings, rather than inside the Character sheet. character.html no longer shows any of it — the Level/XP header, Character Stats box, Perks card, and Special Attacks card were removed from character.html entirely and rebuilt on the new page (`renderProgression`/`renderSkillList`, `PERKS`/`MOVES`), leaving character.html back to identity/Health/Stamina/Equipment/Accessories/Purse/basic info. The combat-facing half (`combatSpecial`, `MOVES`, `hasPerk`, etc.) was already in index.html and is unaffected. See [secondary-pages.md](secondary-pages.md) for the full page breakdown.

**Perks + Special Attacks reworked into one Cyberpunk-2077-style skill tree — done.** Per the project owner, skills.html's flat Perks list and Special Attacks list read as two disconnected cards; they're now a single branching tree per stat (`ALL_SKILLS` merges `PERKS`/`MOVES`, grouped into tiered columns by `req`, connected node-to-node), with a shared detail panel below the tree showing whichever node was last tapped. Purely presentational — same shared skill points, same `goblinwar_skills` storage, same stat gating as always; see [player-state.md](player-state.md)'s "Leveling & stats" for the full node-by-node breakdown of what didn't change.

## Quests — index.html — in progress

**Built so far:** four quest types across two sources — see [quests.md](quests.md) for the full mechanics. The Quest Board (any settlement, a fifth action alongside Inn/Marketplace/Work/Talk to Townsfolk) offers minor delivery jobs — a coin flip per slot between Deliver a Message and the heavier-paying Deliver Cargo — capped per settlement tier (village 1, town 2, city 2, capital 3) and reset once a real in-game month rather than daily, with each slot's actual count independently rolled from 0 up to that tier's cap. Delivery targets exclude enemy territory (alliance-relative, not kingdom-specific — see [factions-and-territory.md](factions-and-territory.md)) and reward scales with real travel distance from the giver, shown next to the quest as a travel-time estimate. A Notable Figure (a new sixth action, but only at the handful of specific settlements one of the 5 named `NOTABLE_FIGURES` calls home — not every City/Capital) offers one important kill-task at a time, capped globally so only one can ever be active: Deal with the Bandits at peace, or Drive Off the Raiders (the actual Goblin/Ork threat, paying more) once that figure's home kingdom is at war — reacting to real game state the same way Marketplace pricing already does. Figures are pinned to their home settlement rather than reassigned daily, and disappear (the action stops appearing, any accepted quest is unaffected) if that settlement is captured by another race — see [factions-and-territory.md](factions-and-territory.md). This was a deliberate split from the project owner: important quests come from talking to a character, minor busywork from a board — see "Talkable NPCs" below for how the Notable Figure relates to that still-unscoped idea.

**Quests tab, map markers, and Abandon — done.** A dedicated [quests.html](quests.html) toolbar tab (see [context/secondary-pages.md](context/secondary-pages.md)) lists Active Quests (each with an Abandon button) and a new Recently Completed history (`goblinwar_completedQuests`, capped at 20 entries — the "no completed-quest history" gap below is resolved). Every active delivery quest's destination also gets a small flag marker on the map itself (`buildQuestMarkers()`), and the Quests nav icon carries a live count badge of active quests.

**Not built yet:** the tracker's bigger/structurally-different quest ideas — Protect a Caravan, Destroy a Goblin Nest, Train Villagers, Ask for News (overlaps with Talk to Townsfolk), a Faction Reputation Chain (multi-part, tied to standing with a race), and a fuller Randomised Bounty Board. [quests.md](quests.md)'s "Adding a new quest type" section is the pattern to follow for each — the delivery and kill families already proved it generalizes cleanly (each went from 1 type to 2 without touching the turn-in architecture), these remaining ones are just less well-suited to either existing family.

**Petition for Troops — built, but as a Palace action rather than a `goblinwar_quests` entry.** The idea (travel to a kingdom that isn't at war and convince its royalty to reinforce a threatened ally) turned out to fit the existing Palace flavor-panel better than the Deliver/Kill quest families: the trip to that specific Capital already *is* the "go there" part, and convincing a court is one conversation, not a multi-stage travel-then-turn-in task — so it resolves instantly on accept rather than needing a persisted active quest. See [factions-and-territory.md](factions-and-territory.md)'s "Alliance reinforcement" section for the full mechanic (`goblinwar_reinforcements`, `findAllyNeedingReinforcement`, `acceptPetition`) and [locations-and-camp.md](locations-and-camp.md) for where it hooks into the Palace action. Reward is 20-40 gold / 15-25 XP, same seeded-offer pattern as the Quest Board/Notable Figure.

## Equipment — done; Accessories — done

Equipping is real: six core `MARKET_ITEMS` entries (Sword, Shield, Leather Cap, Leather Armour, Leather Boots, Lucky Charm) each carry a `slot` and a `dmg`/`def` combat bonus, `goblinwar_equipped` tracks what's in each of the 6 slots, inventory.html is where you equip/unequip (an Equip/Unequip button per equippable item row), character.html shows what's equipped and lets you unequip from there too, and `combatAttack()` (index.html) actually applies the bonus to damage dealt/taken — see [player-state.md](player-state.md) and [combat.md](combat.md) for the full mechanics.

**Accessories — done.** The 8-slot grid on character.html is no longer decoration: 8 more `MARKET_ITEMS` entries (Ring of Vigor, Band of Warding, Amulet of the Wilds, Clasp of the Wayfarer, Warbelt, Iron Bracers, Silver Earring, Sigil Charm) each carry their own `slot` id (`ring_left`, `ring_right`, `amulet`, `cloak`, `belt`, `bracers`, `earring`, `charm`) and a small `dmg`/`def` bonus, using the exact same `goblinwar_equipped`/`ITEM_STATS`/equip-button machinery as the original 6 gear slots — `EQUIP_SLOTS` (index.html, inventory.html) just grew from 6 entries to 14. character.html splits its own rendering into two grids off one shared `renderSlotGrid(gridId, slots)` helper (`equip-grid` for the original 6, `accessory-grid` for the new 8) so the visual 3×2/4×2 split stays. inventory.html no longer has a separate grid at all anymore (see "Inventory consolidated into one flat list" below) — all 14 slots' equip state shows inline on each item's own row instead. Buying, selling (with sell-the-last-copy auto-unequip), and the Marketplace listing all worked with zero special-casing, since both pages already drove every equip surface off the shared `EQUIP_SLOTS`/`ITEM_STATS` arrays rather than hardcoding the original 6.
- **Inventory consolidated into one flat list — done.** Per the project owner, inventory.html's separate Equipment & Accessories slot-grid (below the Carried Items list) was redundant — every equippable item already got its own Equip/Unequip button and highlight in that list. The grid (and its unused `SLOT_LABEL`/click-to-unequip code) is gone; character.html's own two grids are untouched (equip/unequip works differently there — display plus unequip-only — see [secondary-pages.md](secondary-pages.md), and any further merging is bound up in the Hero Screen design conversation, see below). Item rows on inventory.html are also visually smaller now (tighter padding, a 19px icon instead of 26px), since a fuller bag was starting to make the page feel long.

**A Marketplace/Blacksmith equip hint, and Dropping an item — both done.** Every equippable row now shows an "Equips: {slot}" tag before you buy it (`EQUIP_SLOT_LABELS`, index.html — see [locations-and-camp.md](locations-and-camp.md)), so you no longer have to buy something and check inventory.html just to learn its slot. inventory.html also grew a Drop button on every row (`consumeItem`, auto-unequipping the last copy of an equipped item the same way selling does — see [secondary-pages.md](secondary-pages.md)), the answer to the old "no way to destroy an item for no gold" gap.

What's still not built: stacking multiple bonus *sources* per slot (each slot holds exactly one item, as intended, but there's no rarity/tier variation — a Sword is always +4, forever, and so is a Warbelt) — the Blacksmith's second tier (above) is still the only answer to that, not a per-instance upgrade system.

## Party / Companions — party.html

**The roster/portrait system is built, and recruiting is real now too.** index.html has a `COMPANIONS` catalog array (`{id, name, title, portrait, blurb, homeBurgId}` per entry, following the same one-array-entry-plus-a-PNG pattern as `ENEMY_VARIANTS`/`NOTABLE_FIGURES` — party.html duplicates a leaner copy without `homeBurgId`, per the no-modules convention — see [secondary-pages.md](secondary-pages.md)) and a `goblinwar_party` `localStorage` key (JSON array of recruited companion ids, part of the character snapshot shape, see [characters.md](characters.md)) that drives which of them actually show up. `MAX_PARTY_SIZE` (`3`) caps how many can be active at once (companions and mercenaries share the cap), per the project owner — shown as a live "n / 3" counter on party.html.

**The three companions — Ser Brannoc Ward (human knight), Wren Sable (human mage), Thrain Emberforge (dwarf warrior)** — are original characters, deliberately distinct from both the existing unused knight/mage/dwarf roster in Character Forge and from Natasha/Sophie, which the project owner confirmed are staying out of the party system. All three have real generated art (`assets/party/brannoc-ward.png`, `assets/party/wren-sable.png`, `assets/party/thrain-emberforge.png`, set as each entry's `portrait`), also attached back to their Character Forge tracker entries (`hasImage: true`).

**Recruiting — done.** Per the project owner: "have them in random cities, but you have to talk to them to hire them — they give you their story and why they want to join, and you decide." Each companion is pinned to one home settlement (`homeBurgId`) spread across different cities than `NOTABLE_FIGURES` uses, and Thrain (a dwarf) sits in Dwarf territory rather than Human, matching his own race. A new "A New Face" settlement action (`getCompanionForBurg`, same disappears-if-captured/already-taken rule `NOTABLE_FIGURES` uses, city/capital tier only) opens `showCompanionPanel` — the companion's name, title, and `blurb` (their own spoken reason for wanting to join, reused verbatim), with **Not Now**/**Recruit** buttons rather than a mercenary's instant paid hire. Declining isn't remembered; the same companion is there to talk to again next visit. A full party shows that instead of a Recruit button. Recruited companions get their own **Part Ways** button on party.html (`partWithCompanion`) to free the slot back up, worded differently from a mercenary's Dismiss since they're not a paid employee.

**Still not built:** combat participation, or the loyalty meter (see "Companion loyalty" below) — a recruited companion is just a roster entry today, the same gap mercenaries had before their own combat participation shipped (see [combat.md](combat.md)'s "Party in combat"). This is also why the `permadeathCompanions` difficulty toggle (see "Difficulty setting — permadeath" below) is still inert even though companions can now actually be recruited — there's no fight yet for one to die in.

## Smaller/implicit gaps (not marked with a UI stub, but visible from the code)

- **Hunger & Thirst — done.** Replaced the old per-trip Food-cost gate entirely — see [player-state.md](player-state.md)'s Hunger & Thirst section for the full mechanic. Food and Waterskin are the game's two real consumables: inventory.html's item rows grow **Eat**/**Drink** buttons (`eat-food-btn`/`drink-waterskin-btn`) that consume one and relieve Hunger/Thirst by a flat amount, disabled once the relevant meter is already at 0 — the first "use a consumable" interaction in the game, so this is the pattern to extend if Healing Potion/Books/Firewood ever get one too. Neither restores Stamina anymore (an earlier build briefly had Waterskin do that; reversed at the project owner's direction once Hunger/Thirst existed as the real place for it to land). Both meters also rise passively from travel/waiting and from combat (win, lose, or flee alike — see [combat.md](combat.md)); left unattended, either overflowing past 100 converts the excess straight into Health damage, floored so starvation/dehydration alone can never be fatal. Bedroll is no longer a flavor-only possession: it's now an expensive (45g) Marketplace purchase that, carried, both multiplies the night-ambush roll by `BEDROLL_AMBUSH_MULT` (0.85, stacking with the Sure Feet perk's own 0.9) *and* grants a `BEDROLL_STAMINA_BONUS` (15) overcap on top of a full stamina refill after resting — see [locations-and-camp.md](locations-and-camp.md)'s Tavern/Camp rest write-ups. inventory.html still shows this as an informational note on Bedroll's row rather than a button, since both effects are passive.
- **The Pub — done, then merged into the Inn to become one Tavern.** Originally a sixth settlement action gated by tier (every City/Capital, ~40% of Towns via a seeded per-burg coin flip, no Villages) offering an instant "Meal & Drink" for 12g that fully relieves both Hunger and Thirst in one purchase. Per the project owner, having a settlement's rest stop and its food-and-drink stop be two separate locations didn't make sense — **The Inn** and **The Pub** are now **The Tavern**, one action at every settlement (no more tier/coin-flip gating on the meal option), offering Rest for the Night, Meal & Drink, and Tavern Talk together. See [locations-and-camp.md](locations-and-camp.md)'s "The Tavern" section.
- **No character customization.** character.html hardcodes "The Traveler" / "Human" / "Kingdom of Bary" — see "Character creation & race" below, where this ties into a bigger idea from the dev tracker.
- **Three enemy races with several variants each now** (Bandit; Goblin Raider/Shieldbearer/Skirmisher/Archer; Ork Raider/Berserker/Warlord — see [combat.md](combat.md)), but which *race* shows up is still a simple rule (`pickAmbushEnemy`) with no scaling by settlement tier, distance from the frontline, or how long a kingdom's been at war, and there's still no fourth "wildlife"/"monster" category distinct from humanoid raiders.
- **Three more variants, prompted and now added — done.** Goblin Chieftain, Goblin Shaman, and Ork Shaman (see [combat.md](combat.md)'s "Enemy variants and their art") went from Character Forge tracker prompts to real `ENEMY_VARIANTS` entries with generated portraits in `assets/enemies/` — exactly the "one more array entry plus its PNG, no other code changes" the project's own note predicted. Character Forge's three entries are marked `hasImage: true`; `implemented: true` now that they're live in-game too.
- **No random encounters while simply walking around** — only the two fixed ambush rolls (on arrival, on overnight camp) exist; there's no per-day-of-travel "something happens" table beyond bandits.

### World map & travel

- **Weather affects travel** — rain/snow/fog slowing travel speed and reducing map visibility. No weather concept exists anywhere in [travel-and-map.md](travel-and-map.md) today.
- **Points-of-interest markers** — non-settlement waypoints (ruins, camps, river crossings) with their own hover labels and quest hooks, distinct from settlement dots.
- **Day/night cycle — the clock and the visual cycle are done; gameplay hooks are not.** Per the project owner, this was blocked purely on the calendar having no hour-of-day clock — that's fixed now: `gameHour` (0-24 float) is a real, live-ticking clock alongside `gameDay`, advanced by `advanceTime()` for every source of time passing (travel, waiting, camping/resting), shown in the header (`#clock-badge`, a 12-hour `timeStr` readout plus a sun/moon icon) and live during travel the same way Hunger/Thirst already were. A `#night-overlay` tints the map a dark navy at night, ramped smoothly through dawn/dusk rather than an instant cutoff — see [travel-and-map.md](travel-and-map.md)'s "Calendar and the clock" and "Day/night cycle" for the full mechanic. **Still not built:** anything actually reacting to the time of day — ambush odds, NPC availability, and so on are all exactly what they were before this shipped. The clock existing is what unblocks that, not the same thing as having built it.
- **Random world events** — festivals, plagues, or trade caravans spawning near settlements as short-lived opportunities/threats. Distinct from the existing raid/ambush system (see [factions-and-territory.md](factions-and-territory.md)), which is kingdom-vs-kingdom conquest, not a local one-off event.
- **Visible armies on the map** — today `getArmyStrength(kingdom)` (see [factions-and-territory.md](factions-and-territory.md)) is purely an internal number used to weight raid outcomes; nothing renders a moving army or shows who owns it.
- **World map rebuilt as a painterly render — done.** Two earlier approaches were tried and abandoned before landing here: first, a grid of large unique plates painted by Gemini and stitched together (dropped — Gemini couldn't hold a consistent style across that many big, independently-painted regions, even with reference images); then a small reusable pixel-art tileset stamped by a data-driven pipeline (dropped at the project owner's direction in favor of a softer, hand-drawn look — see the reference discussed in the session that built this). What actually shipped needs no external art generation at all: `scripts/build-world-raster/render-painterly.js` (a standalone offline Node tool, its own `package.json`, `sharp` for compositing, `node_modules` gitignored — not part of the game's runtime) renders `assets/world-raster.jpg` directly from `assets/game-map.json`'s real Voronoi cell geometry, biome, elevation, river, and state data:
  - **Soft-blended terrain** — every land cell's polygon is filled with its biome color (or a mountain color above a height threshold), rendered via SVG and then Gaussian-blurred, so biomes blend smoothly into each other with no hard tile edges.
  - **Coastline** — a two-pass chamfer distance transform computes real per-pixel distance-to-nearest-land (not cell-hop distance, which produced blocky, wrong-looking water in an earlier pass), bucketed into 5 concentric color bands that blend warm/sandy near shore to deep navy in open ocean, plus a crisp dark coastline stroke drawn unblurred on top.
  - **Rivers** — traced from `pack.rivers`' actual cell sequences, Chaikin-smoothed (not Catmull-Rom — that extrapolates a tangent through each point and pinches into a cusp on a sharp turn; Chaikin only ever interpolates between existing points, so it can't loop or cusp), tapered from thin at each river's genuine headwater up to full width at its mouth (SVG can't vary stroke width continuously along one path, so this is stepped — a few overlapping sub-segments, each its own width), and extended to the *exact* shared boundary point between the last land cell and the sea (not that cell's centroid, which can sit visibly inland) so every river reaches the coast flush, no gap and no overshoot poking through the coastline stroke.
  - **Forests** — each tree is 2-3 jittered overlapping circles (a fuller canopy silhouette than one dot), dense enough to actually read as forest; Taiga gets small triangles instead, so conifer forest doesn't look identical to deciduous just because both are "green with dots."
  - **Mountain hachures, a dotted land stipple texture, and dashed kingdom border lines** round out the look — see the file's own comments for the SVG-performance traps hit along the way (`opacity` vs `fill-opacity` on thousands of repeated elements pathologically hangs the renderer; a pattern fill repeated per-polygon instead of once as a single masked rect does too).
  - **A later "make it feel alive" pass** added: snow caps (a pale tint layered on the very highest peaks, above `SNOW_HEIGHT_THRESHOLD`, blurred into the base like everything else), soft translucent cloud shadows (a handful of large low-opacity blobs seeded across the whole canvas, land and water alike), and wave texture (small scattered arc marks inside every water cell, denser near the coast where cells are smaller) — the ocean read as too flat/dead without it.
  - **Roads, borders, and settlement markers are untouched by any of this** — per [data-files.md](data-files.md), those are the SVG `#overlay` drawn on top of `world-raster.jpg`, not baked into it.
  - Regenerate with `node scripts/build-world-raster/render-painterly.js` — it writes `assets/world-raster-preview.jpg` (gitignored) rather than overwriting the real asset directly; copy that over `assets/world-raster.jpg` once a change looks right.
- **War frontline tracker / territory border detection — done.** `buildBurgAdjacency()` derives a real burg-to-burg border graph from the existing cell-level road/sea adjacency (see [factions-and-territory.md](factions-and-territory.md)), `isFrontlineBurg()` uses it to flag any settlement actually bordering enemy territory it's at war with, and `buildFrontlineMarkers()` draws a small ring on each one, rebuilt after every weekly tick. Raid/siege targeting (`pickRaidTarget`) now prefers a real border settlement over the old proximity-to-centroid guess too. Not yet used to sharpen Alliance Reinforcement's ally pick (still least-reinforced rather than proximity/border-based) — a possible small follow-up, not scoped.
- **Procedurally generated per-game kingdoms/borders — idea only, raised by the project owner, refined but not scoped.** Today's kingdom identities, names, and territory come straight from the Azgaar export baked into `travel-graph.json` (`graph.burgs[id].state`/`.race`, see [data-files.md](data-files.md)) — the same political map every character starts from (each character's own *war/conquest progress* is already independent, per [factions-and-territory.md](factions-and-territory.md)'s Persistence section, but the starting borders/kingdom names themselves are fixed). The idea: reassign which *area* of the map each kingdom controls fresh per new character, so replaying feels different each time, while keeping settlement names and the kingdom-name pool exactly as they are today — nothing needs inventing:
  - **Settlement names never change** — already true today, and stays true; only *which kingdom* a settlement belongs to would vary.
  - **Kingdom names are a fixed, reusable pool, not generated per game** — the same ~24 names (now race-appropriately titled, see [data-files.md](data-files.md)'s note on the Ork/Goblin kingdom rename) get reassigned to different territory each game, rather than needing a name generator. Since race-appropriate titling is already sorted per kingdom (Human/Dwarf-style vs. Ork/Goblin-style), a new game's generator just needs to pick a name from the *correct race's* pool for whichever region it's assigning that race to.
  - **`NOTABLE_FIGURES` follow their kingdom, not a fixed settlement** — per the project owner's suggestion, pin each figure to a *kingdom identity* rather than a literal `homeBurgId`; wherever that kingdom's capital ends up on a given game's regenerated map is where the figure appears. Avoids the current design's problem of a figure ending up in territory that no longer matches them once borders move.
  - **The still-unsolved, genuinely large part**: real settlement/race assignment has to come from *contiguous* region-growing (a flood-fill-style clustering by alliance, similar in spirit to `buildBurgAdjacency`'s own BFS) rather than per-settlement randomness, or the Good/Bad frontier the whole war system leans on would come out as an incoherent checkerboard instead of a real front line. This is the one piece that's still real, unscoped work — everything else above is now a naming/reassignment problem, not a generation problem.
  - Whatever shape this takes, **war must stay restricted to the Good alliance (human/dwarf) vs. the Bad alliance (ork/goblin) exclusively** — never human vs. dwarf or ork vs. goblin — which is already how `ALLIANCE`/the relations-matrix pair loop in `runFactionAITick` works today (see [factions-and-territory.md](factions-and-territory.md)) and would need to carry over unchanged into any regenerated map.

### Settlements

- **Unique per-settlement art** (a generated picture per visited settlement, replacing the four generic tier illustrations in `TIER_ART` — see [locations-and-camp.md](locations-and-camp.md)), with graduated variants reacting to war state rather than a single fixed look per tier: a **war/border variant** (fortifications, banners, visible unease) for a settlement whose kingdom is at war *and* sits near enemy-controlled territory — needs the border-detection concept above to know which settlements actually qualify as "on the border" — and a **destroyed/raided variant** for after a settlement actually changes hands. Same tier + state combination should render consistently everywhere that settlement's art shows up (the location-view corner box today, and `showLocationView`'s subtitle already has separate `(captured)` text that a matching art variant would reinforce visually rather than duplicate).
- **Settlement prosperity**, distinct from the population number that already exists — population currently only feeds war attrition/refugees/army strength (see [factions-and-territory.md](factions-and-territory.md)); Marketplace pricing still only reacts to kingdom-wide war/peace, not a per-settlement prosperity figure.
- **Trade goods / arbitrage economy** — buy-low-sell-high goods (cloth, ore, grain) between settlements. `MARKET_ITEMS` prices are the same everywhere modulo the war multiplier; there's no per-settlement price variation to arbitrage.
- **Horse travel — done.** A purchasable `MARKET_ITEMS` entry (weight `0`, not equippable, just carried like Bedroll) that cuts road-travel `hours` by `HORSE_PACE_MULT` (1.5×) in `computeTravel` — see [travel-and-map.md](travel-and-map.md)'s "Horse and ferry fares" section. Doesn't speed up a sea crossing.

### Character creation & race

- **Character creation at new-game — starting city choice done, race/origin still not built.** characters.html's Create New Character form now includes a **Starting City** picker (`populateStartCitySelect()`) — every Human-race settlement of tier `city` or `capital` from `travel-graph.json` (15 today), capitals sorted first, Bary preselected to match the old hardcoded single start. `freshCharacterData(name, burgId)` threads the choice through. Still not built: choosing a race/origin that determines starting stats and which alliance (Good/Bad) you begin aligned with — "Human" is still the only race a character can ever be, and this picker is deliberately Human-only per the project owner (a fresh character never starts in Dwarf/Ork/Goblin territory), so it doesn't get you any closer to that part of this idea.
- **Race-specific traits** — the tracker's Races data models Human/Dwarf as "stronger equipment, better tactics" and Ork/Goblin as "multiply more quickly," none of which is wired into any gameplay system yet (this would presumably hook into the same Strength/Agility/Intelligence system in the Skills & Progression section above, e.g. as starting stat bonuses).
- **Religion per faction** — lore-only idea, no gameplay hook proposed yet.
- **Difficulty setting — permadeath — done, all three toggles.** Raised by the project owner while scoping mercenary combat (see [combat.md](combat.md)'s "Party in combat"), built as a choice made once, at character creation (characters.html's create form, alongside the Starting City picker) — three independent checkboxes rather than one global switch, defaulting to exactly the game's original pre-this-feature behavior (player off, companions/mercenaries on) so no existing character's play changes silently:
  - **Player** — on makes losing a fight game over: `endCombat`'s `'defeat'` branch sets `isDead` on the character (instead of the old unconditional `setHealth(10)` safety net), explicitly awaits one save (unlike the routine keepalive-backed autosave elsewhere — this one-time write is worth the wait), then redirects to characters.html after a beat to read the toast. A dead character's card there shows a "Deceased" badge and no Play button — `playCharacter()` also refuses on the data itself as defense in depth. Off keeps today's behavior exactly (`setHealth(10)`, keep playing).
  - **Companions** — stored and round-tripped (`permadeathCompanions`, unused in index.html today) but still genuinely inert. Recruiting a companion is real now (see "Party / Companions" above), but they don't fight and have no loyalty meter yet — there's simply no way for one to die yet, permadeath toggle or not. Locking the field in now means combat participation, whenever it ships, won't also need its own snapshot-shape migration.
  - **Mercenaries** — on matches the unconditional behavior mercenary combat already shipped with (see [combat.md](combat.md)'s "Party in combat"); off is the new case, and lets an easier difficulty turn that off instead of ripping the mechanic out: `mercenaryFalls()` now only removes a mercenary from the roster permanently when this is on — off, they're merely knocked out of the rest of that one fight and roster back in fully healed next time, same as the player's own no-permadeath default.
  Four new snapshot fields (`isDead`, `permadeathPlayer`, `permadeathCompanions`, `permadeathMercenaries`) — see [characters.md](characters.md). Read-only after creation; settings.html shows the chosen values (`#current-difficulty`) so a player can recall them, but there's no way to change them mid-playthrough, deliberately — it's a character-creation choice, not a live setting.

### Hero screen — awaiting a design conversation with the project owner

**Character portrait — a picker, not just a frame.** The project owner raised choosing a character portrait from a list of already-generated art (presumably Character Forge's growing human/dwarf roster — see "Talkable NPCs" above for where that tracker is) as part of rethinking how the Hero screen (character.html) works overall, then asked to talk through the design before any of it gets built — nothing here is scoped yet, deliberately. Distinct from the "Character portrait frame + rune border"/"Character portrait sprites" bullets in the UI Theme section below, which are about styling an empty placeholder slot as part of the blue/gold reskin, not about letting a player actually pick a portrait. Open questions for that conversation: which portraits are selectable (all of Character Forge's roster, or a curated subset), whether the choice is made at character creation or changeable later from the Hero screen itself, and how it interacts with the still-unbuilt race/origin picker above (a race choice would presumably narrow which portraits are offered).

### Combat

- **Pre-fight story beat — done.** Every fight (`startCombat`, the shared entry point every current trigger goes through — ambushes and Defend the Walls, see [factions-and-territory.md](factions-and-territory.md)) now opens with one line from `COMBAT_INTRO_LINES`, shown above the existing mechanical "X blocks your path!"/"N enemies block your path!" line in the combat log — a small, scene-agnostic narrative beat so a fight reads as a moment in the player's own story rather than just a stat check. `triggerSiegeDefenseFight` appends its own siege-specific line rather than overwriting the log, so the beat survives there too.
- **Status effects** — bleed, stun, or fatigue as modifiers layered on top of the existing turn-based Attack/Specials/Flee loop (see [combat.md](combat.md)).
- **Combat environment backgrounds — idea only, raised by the project owner, art to be generated later.** Replace `#combat-view`'s flat background with a real illustrated scene behind the enemy portrait cards, matching the encounter's setting — a forest backdrop for a forest ambush, the besieged settlement's walls for Defend the Walls, and so on — so the player has a visual sense of *where* a fight is happening, not just who it's against. Generation prompts are tracked in the new "Combat Backdrops" tracker artifact (ask for its link if it's not at hand), one card per environment/context, composed as a wide plate meant to sit behind the existing `.combat-enemy-slot` cards rather than replace them — full custom scenes painted per unique enemy combination would be a combinatorial explosion of art, so a shared backdrop layer is the practical approach. Two things need deciding before this can actually wire in, once art exists:
  - *Which backdrop to show* — the live game has no biome/terrain concept anywhere today; `travel-graph.json` doesn't carry it, and while the raw `assets/game-map.json` Azgaar export does (see [data-files.md](data-files.md)), nothing currently pulls it through. Until that data pipeline exists, backdrop selection would have to key off combat *context* instead of true biome — the "Road / Wilderness", "Night Camp", and "Under Siege" cards already in the tracker cover the three contexts the game actually distinguishes today (`triggerAmbushFight`'s `context` param, and Defend the Walls).
  - *How selection ties into `startCombat`* — nothing in the current code threads a biome/context value down to where the combat view actually renders; that plumbing (probably a new optional `startCombat` parameter, or a module-level "current backdrop" set right before each trigger call) is unbuilt.

### Open design question worth flagging

The tracker's "Skills & Combat" tab describes an older, different idea: a Skyrim/Bannerlord-style skill list trained by *using* it (One-handed Weapons, Two-handed Weapons, Bow & Arrow, Medium/Heavy Armour, Healing, Horse Riding, Trade/Charisma, Cooking/Leadership), with an explicit open question of learn-everything vs. a capped build. That predates and doesn't match the Strength/Agility/Intelligence + skill-point perks/moves system now actually built (see the Skills & Progression section above). Worth a decision from the project owner on whether that older idea is superseded, or meant as a second, complementary "proficiency" layer to add later alongside stats/perks.

### Living world (large, mostly unscoped)

Still just one-line ideas in the tracker, no design decisions made on any of these: marriage/romance, NPC memory (reacting differently based on player actions — ties into the Talkable NPCs idea above), a reputation system, character death with some form of legacy, and NPC children existing in the world. Item rarity/tiers is already tracked above under Equipment (a Sword is always +4, forever). Sieges/garrisons and a pairwise kingdom relations matrix are now built — see [factions-and-territory.md](factions-and-territory.md); that file's own "Known simplifications" section tracks what's still cut from that system specifically (no garrison-vs-attacker battle simulation beyond a strength-ratio roll, no diplomatic memory behind Negotiate Peace).

One thing the tracker records as **already decided**, not just an idea: the player is meant to grow strong but never able to solo-topple a city — a support-role cap on player power, worth keeping in mind whenever combat or army-strength numbers get revisited.

## Future ideas from AI-assisted brainstorming (2026-09-09, not from the dev tracker)

Everything below came out of a brainstorming pass with an AI assistant, not `Goblin_War_Tracker.xlsx` — kept in its own section rather than folded into "Future ideas from the dev tracker" above so this file stays honest about where each idea actually came from. Same status as that section otherwise: pure brainstorm, nothing scoped, nothing with a code stub.

### World map & travel

- **Fog of war** — unvisited regions of the map render darkened/hazy until the player has actually traveled near them, rather than the whole map (all settlements, roads, terrain) being visible from a brand-new game. Would need a persisted "revealed" mask keyed off logical-space position, checked and grown as travel updates the player's position — see [travel-and-map.md](travel-and-map.md) for where that position tracking already lives.
- **Off-road landmarks/ruins** — optional points of interest away from the settlement/road network entirely (distinct from the "Points-of-interest markers" idea above, which is about waypoints *on* known routes), each a small self-contained risk/reward beat: a fight, a piece of lore, a one-off loot find. Reaching one would need its own off-road travel affordance, since today's travel is always settlement-to-settlement along `travel-graph.json`'s road/sea graph.
- **Contested bridges/fords** — a chokepoint edge in the road graph that gets toll-taxed or closed outright while the kingdom controlling it is at war, forcing a detour through `buildAdjacency()`'s pathfinding rather than the shortest route always being available. Would tie into the same war-state checks `getBuyPrice`/`isAtWarAt` already do for Marketplace pricing (see [factions-and-territory.md](factions-and-territory.md)).
- **Paid ferry crossings — done, as a fare on every sea leg rather than only the widest gaps.** `computeTravel` derives `ferryCost` from the route's own sea mileage (`routeBetween`'s new `seaMiles`) and `beginTravel` gates on it — a real affordability gate, unlike Hunger/Thirst's deliberately-never-blocking design — see [travel-and-map.md](travel-and-map.md)'s "Horse and ferry fares" section.

### Settlements & economy

- **Blacksmith — done, via a second-tier item catalog rather than a per-instance upgrade.** [locations-and-camp.md](locations-and-camp.md)'s "The Blacksmith" — City/Capital only, a near-duplicate of `showMarketPanel` selling only `shop:'blacksmith'`-tagged `MARKET_ITEMS` (Masterwork Sword, Reinforced Shield, Steel Helm, Plate Armour, Steel Greaves, Warrior's Talisman — one per core Equipment slot, roughly double the bonus at roughly triple the price). The idea originally here was upgrading an *already-owned* item's `dmg`/`def` in place; that would have needed inventory items to carry individual identity instead of stacking by name/qty, a bigger rework than this ask called for, so a second fixed tier via a second item name shipped instead — still a real (if smaller) answer to the Equipment section's "no rarity/tier variation" gap above.
- **Property ownership** — buy a house in a specific settlement as a permanent base, granting a free-rest perk there (skipping the Tavern's gold cost, though not necessarily its rumour) and maybe a personal storage chest beyond `CARRY_CAPACITY` (see [player-state.md](player-state.md)).
- **Palace loans** — borrow gold at a Capital against future Work income, with real interest accruing over `gameDay`s and a real consequence for defaulting (e.g. that kingdom's services refusing the player until repaid) — a new Palace card alongside the existing Petition for Troops/Negotiate Peace ones (see [factions-and-territory.md](factions-and-territory.md)).
- **Settlement specialties — a small, scoped slice done; the original idea's fuller version still not built.** `getSettlementDiscount` (index.html) discounts Waterskin at a port settlement and Food at a Village, off data `travel-graph.json` already carries (`b.port`/`b.tier`) — see [locations-and-camp.md](locations-and-camp.md). Sits alongside the existing per-kingdom war-price multiplier, doesn't replace it. The original ask here (a mountain Town discounting armor-slot items) is still unbuilt: the live game has no elevation/biome data pulled through yet (same gap noted under "World map & travel" below), so a real mountain check isn't possible without that pipeline first.
- **Gear durability** — equipped items lose a small amount of `dmg`/`def` with combat use, needing an occasional repair fee at the now-real Blacksmith (see above) to restore — a new, ongoing gold sink beyond Food/Waterskin, since equipment today never degrades once bought.

### Combat

- **Named unique bosses** — a one-off chieftain/warlord `ENEMY_VARIANTS`-style entry with its own generated portrait, higher stats than any existing variant, and a guaranteed strong loot roll, offered as the target of a Notable Figure kill-quest (see [quests.md](quests.md)) rather than ever showing up from a random `pickAmbushEnemy` roll — a fight worth traveling for, not one that can just happen to you.
- **A real flee cost — done, exactly as sketched here.** `combatFlee` (see [combat.md](combat.md)) still always succeeds — no roll, no Stamina cost, so a player who's run out of Stamina can never be soft-locked into a fight — but `endCombat`'s `'flee'` branch now adds a flat Hunger/Thirst hit (`FLEE_HUNGER_PENALTY`/`FLEE_THIRST_PENALTY`) on top of the exertion every combat outcome already pays, routed through the same overflow-to-Health floor as everything else in [player-state.md](player-state.md)'s Hunger & Thirst section — so fleeing broke stings but never traps the player.

### Progression

- **Prestige / New Game+** — once a character can actually reach max level, let a fresh playthrough carry over a portion of banked skill points or a cosmetic title, rather than leveling being a purely one-shot, one-save arc.
- **Titles on the character sheet — a small, scoped slice done; the fuller Achievements-page idea below still isn't.** Three cosmetic titles (Bandit Hunter, Goblin Bane, Ork Slayer) now show on character.html next to identity once `goblinwar_kills` clears a threshold — see [player-state.md](player-state.md)'s "Titles" section. Still exactly what it was scoped to be: no stat effect, no per-title icon, no milestone list beyond these three — a lightweight layer distinct from the "Achievements page" idea below, not a first slice of it.
- **A "use it to level it" proficiency layer** — the "Open design question worth flagging" section above already notes the dev tracker's older Skyrim/Bannerlord-style skill-list idea predates and doesn't match the built Strength/Agility/Intelligence + perk-point system. One way to resolve that open question without discarding either idea: layer proficiency-by-use *on top of* the existing system rather than replacing it — e.g. landing enough Sword-equipped attacks in `combatAttack()` slowly unlocks a Swordsmanship perk, entirely additive to the Str/Agi/Int skill points already spent.

### Party & Companions

- **Hireable mercenaries — done, combat participation included now.** A Guard House action (`buildMercenaryHireHTML`/`hireMercenary`, index.html — see [locations-and-camp.md](locations-and-camp.md)) hires from a small fixed `MERCENARY_TYPES` catalog (Hired Sellsword/Mercenary Archer/Veteran Guard) into a new `goblinwar_mercenaries` key, sharing `MAX_PARTY_SIZE` (3) with `goblinwar_party`. Upkeep is charged from `advanceDays(n)` rather than a per-settlement `hasWorkedToday`-style cooldown (that pattern fits a *place* you have to revisit; upkeep needed to keep accruing no matter where the player was) — `chargeMercenaryUpkeep()` bills every elapsed day in one lump sum whenever the calendar advances for any reason (travel, camping, resting), and drops any mercenary the player can't currently afford, with a toast naming who left. Deliberately anonymous per the project owner (no name, just a role) — but each role does have real generic portrait art now under `assets/mercenaries/` (faceless by design: full helm or a shadowed hood, never a face), keeping mercenaries visually and narratively distinct from the named, real-portrait `COMPANIONS` catalog. **Also done:** hired mercenaries fight alongside the player in `combat` — see [combat.md](combat.md)'s "Party in combat" — dealing damage automatically each round and able to draw (and die permanently to) an enemy's counter-attack in the player's place.
- **Recruitable companions — the recruit action is done; combat participation and loyalty are not, and are two separate remaining steps.** Per the project owner: "have them in random cities, but you have to talk to them to hire them — they give you their story and why they want to join, and you decide." Each `COMPANIONS` entry (index.html) is now pinned to a home settlement (`homeBurgId`, spread across different cities than `NOTABLE_FIGURES` — Thrain, a dwarf, in Dwarf territory rather than Human) with a new "A New Face" settlement action opening a conversation panel — their story (`blurb`) plus Recruit/Not Now, not an instant paid hire like a mercenary. See "Party / Companions" above for the full flow. Unlike mercenaries, a recruited companion still doesn't fight (see [combat.md](combat.md)'s "Party in combat" for what that would need to look like) and still has no loyalty meter (next bullet) — recruiting them was the first of three separate steps this idea always had, not the whole thing.
- **Companion loyalty — for recruited companions, not hired mercenaries — still not built.** Per the project owner: a paid mercenary is a simple cash transaction (leaves if upkeep goes unpaid, no feelings involved), but a *recruited* companion (the kind Talkable NPCs' Natasha/Sophie idea above gestures at, not a hired sword) would carry a real approval meter nudged by player choices — aiding refugees vs. warmongering, Negotiate Peace vs. letting a war run — affecting whether they stick around. Two distinct companion categories, one with loyalty and one without, not a single unified system. This is also why `permadeathCompanions` (see "Difficulty setting — permadeath" above) is still inert despite recruiting now being real — no combat, no loyalty, nothing yet for a companion to be lost *from*.
- **Companion quests** — one small personal quest per recruited (non-mercenary) companion, reusing the existing Deliver/Kill quest turn-in architecture [quests.md](quests.md) already documents rather than inventing a new quest family.

### Faction war & quests

- **Kingdom elimination — needs real design work, sketched below rather than fully scoped.** Today a kingdom keeps existing in the war/relations matrix forever regardless of how many of its settlements have been captured — `runFactionAITick` still rolls war/peace and siege chances for it every week, and `WAR_ATTRITION_RATE` still bleeds population from its *originally*-owned settlements (`b.state`) even ones it no longer controls, per [factions-and-territory.md](factions-and-territory.md)'s own "Known simplifications". The idea: once every settlement whose `b.state` is kingdom X has been captured (`getController(burgId) !== b.race` for all of them), treat X as eliminated —
  - Skip it entirely in `runFactionAITick`'s per-kingdom attrition/siege loop and its relations-matrix pair rolls (nothing left to attack from or defend), rather than continuing to simulate a kingdom with zero territory.
  - Give it a distinct one-time announcement, the same way `maybeRunFactionAI()` already summarizes captures in a toast — "the Warg Horde has fallen" reads as a bigger moment than an ordinary settlement-capture toast and probably deserves different treatment (a modal, not just a toast).
  - Its captured settlements simply stay with their conquerors — no separate "kingdom is gone, territory reverts to neutral" step, consistent with `setController` already being one-way with no restore-original-owner action.
  - Open questions this doesn't answer yet: whether an eliminated kingdom's `NOTABLE_FIGURES` entries (if not already gone via their home settlement being captured) should be explicitly retired too; whether losing a whole kingdom should shift `getArmyStrength`-based numbers for the rest of its alliance (one less Bad-alliance kingdom presumably makes the Good alliance's overall position stronger, but nothing today aggregates strength above the single-kingdom level); and whether elimination should ever be reversible if the procedurally-generated-territory idea (see "World map & travel" above) ever lands and a new game redraws the map from scratch anyway.
- **Per-kingdom reputation** — standing gained or lost through quests, Aid the Refugees, Negotiate Peace, or combat against a given race, tracked separately from the live war/peace relation itself (which [factions-and-territory.md](factions-and-territory.md)'s "Known simplifications" already flags as having no memory of its own). High standing could unlock better Marketplace prices or unique quests at that kingdom; very low standing could turn its Guard House hostile on sight.
- **War exhaustion** — the longer a specific war relation has been active, the more it passively pressures both kingdoms toward `WAR_PEACE_CHANCE`'s roll succeeding (or a growing bonus stacked on top of it), so a war doesn't just run indefinitely at the same flat 15%-per-week chance to end — giving the player's own Negotiate Peace option a real ticking clock it's racing against rather than being the only thing that ever ends a war.

### Living world

- **Aging effects** — character.html already tracks age (currently just displayed, no gameplay hook). Crossing age thresholds over a long playthrough could trade off small stats — e.g. reduced Stamina regen, increased Intelligence — rather than age being purely cosmetic forever.
- **Seasons** — a slow calendar-driven cycle (independent of, and slower than, the "Day/night cycle" idea above) tinting the world-raster/biome art and swapping in seasonal settlement flavor lines (a harvest-festival line pool in autumn, etc.) — a longer-timescale companion to weather rather than a replacement for it.
- **Reactive rumors, intended to eventually fully replace the static flavor pool.** Per the project owner, the end state isn't just adding reactive lines alongside `RUMOURS` — it's `RUMOURS` (and likely `TOWNSFOLK_LINES_*`/`WORK_LINES` alongside it) eventually going away entirely, replaced by lines generated from real faction-AI state (an active `goblinwar_sieges` entry, a kingdom recently eliminated per the idea above, a settlement that's changed hands) so every flavor line the player reads is describing something that's actually true in their specific game, not a fixed pool of generic color. A real migration, not a quick addition — every current flavor-line consumer (`showInnPanel`, `getTownsfolkLines`, `doWork`) would need its static array replaced by a generator function, one at a time, likely leaving some pools static for a while as others convert.

### Meta / UX

- **Achievements page — done, via a Settings menu item rather than a toolbar tab.** [achievements.html](../achievements.html) (see [secondary-pages.md](secondary-pages.md)) is the dedicated completionist checklist this idea asked for: every Capital visited, every `ENEMY_VARIANTS` entry defeated at least once, cumulative kill/quest-completion/level milestones — five categories, each card a progress bar plus an `X / Y` count. Three new cumulative-only `localStorage` keys back the two checklist categories that had no tracking yet (`goblinwar_visitedBurgs`, `goblinwar_defeatedVariants`, `goblinwar_questsCompletedTotal` — see [player-state.md](player-state.md)); the milestone categories (kills, level) reuse data that already existed. Stays separate from the cosmetic Titles line on character.html, per the original idea — both happen to read `goblinwar_kills`, but neither depends on the other.
- **Colorblind-friendly stat pills — done, via text labels rather than a new icon/palette.** Each of the four `.stat-pill`s in `#player-stats` already used a distinct icon shape (heart/bolt/hunger icon/droplet); a small `.stat-tag` label (`HP`/`STA`/`HNG`/`THR`) was added alongside each icon so meaning never depends on shape or hue recognition at all — the most robust fix, not just an alternate palette. See index.html's `#player-stats` markup.
- **Stale-save warning — done, matching this idea's own design.** settings.html now flags it (a warning banner above the current-character card) if the Supabase `characters` row's `updated_at` is meaningfully newer than `goblinwar_localSyncedAt`, a new device-local marker this browser updates on every successful load/save — see [characters.md](characters.md)'s "Stale-save warning" section for the full mechanic.
- **Party tab specifically still felt slow after the fix above — a second, unrelated root cause, also found and fixed.** Per the project owner, Party kept feeling slow even after navigation itself sped up. Profiling on a throttled ~1.5Mbps connection (closer to real mobile conditions than a fast dev machine) with a full 3-mercenary party found the actual cause: `assets/party/`'s and `assets/mercenaries/`'s portrait PNGs were imported at the same 600px-longest-edge convention `assets/enemies/` uses (270-390KB each), even though neither ever renders larger than a 64px thumbnail anywhere in the game (unlike enemy art, shown up to 210px in combat) — three of those loading at once took **~4.9 seconds** on that throttled connection. Downscaled all 6 existing files (3 companions, 3 mercenaries) to a 200px longest edge instead (34-47KB each, comfortably crisp even at 3x device pixel density for a 64px box) — same scenario now loads in **~0.85 seconds**. See [secondary-pages.md](secondary-pages.md) and the root [CLAUDE.md](../CLAUDE.md)'s asset table for the updated convention; any future companion/mercenary art should be imported at 200px, not 600px.
- **Screen-to-screen navigation felt slow — root cause found and fixed.** Per the project owner, tapping a toolbar icon felt sluggish. Profiling (a scripted browser session against the real Supabase backend, not guesswork) showed the visible page itself was never the bottleneck — the actual cause was `goTo()` (index.html) `await`ing a full autosave PATCH to Supabase (several hundred ms to over a second, real network round trip) before the browser was even allowed to start navigating to the next page, a deliberate choice so the save couldn't be lost to the page unload. The fix keeps that same guarantee without the wait: [assets/auth-client.js](../assets/auth-client.js)'s shared client now sends every request with `keepalive:true` (the fetch spec's own mechanism for a request surviving the page that started it), so `goTo()` fires the save and navigates immediately — verified end-to-end that the save still lands. A second, smaller cost (the active-character existence re-check also run on every page load) is now skipped if it already succeeded within the last minute in the same tab (`sessionStorage`-cached, cleared on a real tab close) — see [accounts.md](accounts.md) for both fixes in full. Deliberately **not** touched: the `?_=` cache-busting on every internal link, which exists to fix a real, already-documented bug (see the root [CLAUDE.md](../CLAUDE.md)'s Conventions section) — undoing that would trade this speed win for a worse, previously-shipped one.
